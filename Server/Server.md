# Сервер Enviriot

Сервер предоставляет общую среду выполнения платформы: загружает компоненты,
управляет их жизненным циклом, поддерживает дерево топиков и последовательно
проводит изменения через движковый тик.

## Границы ответственности

- **Серверный хост** отвечает за загрузку компонентов, порядок запуска, движковый поток и организацию остановки. Штатное завершение и принудительное прерывание имеют разные гарантии.
- **Repository** отвечает за дерево топиков, порядок применения изменений и доставку событий, но не интерпретирует назначение данных.
- **[JsLib](#значения-jsvalue)** задаёт единые правила чтения, подготовки и сериализации значений.
- **[JsExtLib](#среда-javascript)** предоставляет общую среду JavaScript и [применение конфигурации](#применение-конфигурации).
- **[RPC](#rpc)** маршрутизирует именованные действия.
- **[Журнал](#журналирование-и-диагностика)** принимает сообщения от всех компонентов и ограничивает поток повторяющихся ошибок.

Маршрут по механизмам хоста:
[запуск](#платформа-и-запуск) →
[жизненный цикл плагинов](#порядок-инициализации-и-запуска) →
[проход движка](#проход-движка) →
[остановка](#остановка-и-отказ-запуска).
Контракты дерева и его изменений описаны отдельно в
[Repository](Repository/Repository.md); хост определяет, когда вызывается его тик,
но не подменяет правила применения данных.

## Платформа и запуск

**Задача.** Поднять общую среду выполнения и сообщить вызывающему хосту
результат запуска, а не только факт создания рабочего потока.

**Контракт.** Сервер собран для .NET Framework 4.8. Точка входа выбирает
консольный режим или службу; запуск через Mono описан в
[основном README](../README.md#debian).

Входы хоста:

- режим: без переключателя — по `Environment.UserInteractive`, `-s` — служба,
  `-i` — установка и запуск службы Windows, `-u` — её удаление;
  вместо `-` допустим `/`;
- путь конфигурации: по умолчанию `../server.xst` относительно каталога
  исполняемого файла; аргумент с путём существующего файла заменяет его;
- сборка сервера и находящиеся рядом сборки с MEF-экспортами `IPlugModul`;
- конфигурация плагинов в дереве, которую они читают при инициализации.

Перед запуском рабочим каталогом становится каталог исполняемого файла.
Дальнейшая последовательность:

1. На Windows хост захватывает глобальный мьютекс `Global\X13.enviriot`.
   Занятый мьютекс означает отказ запуска; на Mono/Linux эта проверка отключена.
2. В вызывающем потоке MEF собирает состав плагинов и их порядок.
3. Создаётся движковый поток `MainTick`. Он активирует контекст NiL.JS
   **до** инициализации Repository: импорт конфигурации уже может компилировать
   JavaScript, а функция захватывает контекст в момент компиляции.
4. В этом потоке выполняются два прохода:
   [инициализация и запуск включённых плагинов](#порядок-инициализации-и-запуска).
5. После них подключается настройка диагностики, активируется таймер
   пробуждения движка и передаётся результат ожидающему `Program.Start`.

`Program.Start` возвращает `true` после этой последовательности,
не дожидаясь первого регулярного прохода движка. После запуска потока
он ждёт ответ не более 120 секунд; загрузка MEF до запуска потока
в этот интервал не входит.

**Границы и ошибки.** Успешный запуск хоста означает возврат из `Init` и `Start`
всех включённых плагинов, но не подтверждает соединение каждого устройства,
готовность удалённого брокера или завершение начатой плагином фоновой работы.
Смысл готовности конкретного компонента остаётся его контрактом.

`false` означает отсутствие успешного запуска: занят мьютекс, не удалось
скомпоновать плагины, получен отказ их запуска либо истёк срок ожидания.
Эти результаты нельзя смешивать: **тайм-аут не отменяет выполняющийся `Init`
или `Start` и сам по себе не означает завершённый откат**.
Консольный хост после неудачи вызывает остановку и устанавливает код выхода 1;
служба сообщает ошибку и также запрашивает остановку.
Подробности освобождения ресурсов — в
[механизме остановки](#остановка-и-отказ-запуска).

Служба Windows запрашивает у Service Control Manager дополнительные 135 секунд
на запуск. Отдельное ожидание команды установки составляет 30 секунд:
если за это время служба не сообщила `Running`, записывается предупреждение,
но это ещё не признание неудачного запуска. Установка и удаление требуют
прав администратора. При установке задаются попытки восстановления службы:
перезапуск после первого сбоя через 15 секунд, после второго — через 2 минуты;
для последующих сбоев автоматического перезапуска не задано.

**Реализация.** [Program.Main, Start, LoadPlugins, PrThread](Program.cs);
[HAServer.OnStart, InstallService](HAServer.cs);
[JsExtLib.ActivateEngineOnThisThread](JsExtLib.cs).

**Проверки.** Автоматических проверок запуска хоста, мьютекса, ожидания
готовности и взаимодействия с SCM в текущем наборе тестов нет.
[ScaffoldTests.InternalsAreVisible](../Tests/ScaffoldTests.cs) проверяет
доступность внутренних типов для тестовой сборки, а не запуск сервера.

## Движковый поток и плагины

### Порядок инициализации и запуска

**Задача.** Поднимать зависимые компоненты в воспроизводимом порядке
и знать, для каких из них потребуется освобождение ресурсов даже после ошибки.

**Контракт.** Плагин экспортирует `IPlugModul` и метаданные `priority` и `name`.
Хост упорядочивает экспорты по возрастанию `priority`; равный приоритет
разрешается сравнением имён через `StringComparer.Ordinal`.
`Owner` указывает на собственный конфигурационный топик плагина в `/$YS`,
а `enabled` определяет участие в запуске.

Первый проход последовательно читает `enabled` очередного плагина
и, если он включён, вызывает его `Init`. Читать все `enabled` заранее нельзя:
Repository сначала должен создать дерево, из которого остальные плагины
получают настройки.

Второй проход вызывает `Start` в том же порядке, только после успешного
завершения **всех** включённых `Init`. Поэтому во время `Init` предыдущие
плагины уже инициализированы, но ещё не запущены; во время `Start` предыдущие
плагины уже прошли и `Start`. После полного успеха формируется состав
участников регулярного тика.

Текущий состав и причины порядка:

| priority | Плагин | Причина порядка |
|---:|---|---|
| 1 | [Repository](Repository/Repository.md) | Создаёт дерево и импортирует конфигурацию до чтения настроек остальных плагинов. |
| 2 | [PersistentStorage](../plugins/PersistentStorage/PersistentStorage.md), имя MEF `LiteDB` | Загружает сохранённые данные из базы данных. |
| 3 | [Archivist](../plugins/Archivist/Archivist.md) | Получает уже восстановленные топики. |
| 5 | [Logram](../plugins/Logram/Logram.md) | Создаёт исполняемые объекты схем по наполненному дереву. |
| 7 | [MQTT_SN](../plugins/MQTT_SN/MQTT_SN.md) | Поднимает шлюзы для работы с устройствами. |
| 8 | [MQTT](../plugins/MQTT/MQTT.md) | Организует подключения к внешним брокерам. |
| 10 | [WebUI](../plugins/WebUI/WebUI.md) | Его `Start` вызывается после `Start` остальных включённых компонентов. |

Repository собран вместе с сервером и всегда включён, но участвует
в том же жизненном цикле.

**Границы и ошибки.** `enabled` читается однократно при инициализации,
а не перед каждым тиком. Изменение его конфигурационного топика само по себе
не включает и не выключает уже работающий плагин; это не механизм горячей
перезагрузки. Живое [применение отдельных настроек](#применение-конфигурации) —
другой механизм, не меняющий состав запущенных плагинов.

Вызовы `Init`, `Start`, `Tick` и `Stop` выполняются в движковом потоке.
Это не обещание, что весь код плагина однопоточен: фоновые обработчики
и внешние вызовы должны отдельно соблюдать правила доступа к общим данным.
Хост также не проверяет граф зависимостей: выключение нужного другому плагину
поставщика не компенсируется автоматическим включением.

Ошибка `Init` или `Start` прекращает дальнейший запуск и приводит к
[обратной остановке затронутых компонентов](#остановка-и-отказ-запуска).
Эта обработка относится именно к вызовам `Init` и `Start`, а не является
общей транзакцией загрузки: создание MEF-объекта и чтение `enabled`
находятся вне этих обработчиков исключений.

**Реализация.** [IPlugModul, IPlugModulData](IPlugModul.cs);
[Program.LoadPlugins, InitPlugins, StartPlugins, PlugState](Program.cs).

**Проверки.** Отдельных тестов сортировки плагинов, двух проходов запуска,
однократного чтения `enabled` и отказа частично инициализированного плагина нет.

### Проход движка

**Задача.** Последовательно выполнять работу компонентов и переданные
из других потоков результаты, не допуская параллельных проходов самого хоста.

**Контракт.** Таймер только подаёт сигнал пробуждения. На движковом потоке
каждый регулярный проход выполняет:

1. `JsExtLib.Tick`: готовые действия из очереди завершений,
   затем JavaScript-таймеры, срок которых наступил.
2. `Tick` каждого успешно запущенного плагина в порядке его приоритета,
   включая Repository первым среди плагинов.

```mermaid
flowchart LR
  wake["Сигнал таймера"] --> js["Завершения и JS-таймеры"]
  js --> repo["Тик Repository"]
  repo --> plugins["Тики остальных плагинов"]
  plugins --> wait["Следующее ожидание или остановка"]
```

Это порядок вызовов хоста, а не полный граф работы плагинов.
Обработка пакета изменений и доставка подписок внутри `Repo.Tick`
описаны в [механизме Repository](Repository/Repository.md#очередь-изменений-и-тик-repository).
Важно различать **проход движка** и **тик Repository**: например,
команда из `Tick` WebUI поступает уже после вызова Repository в этом проходе
и обычно будет разобрана в следующем. Сам факт работы кода на движковом
потоке не делает `SetState` синхронной записью.

**Границы и ошибки.** Таймер запрашивается с первой задержкой 100 мс
и периодом 5 мс, но это не гарантия фактической частоты или максимальной
задержки реакции. Ожидание построено на `AutoResetEvent`: несколько
сигналов во время долгого прохода могут объединиться, а не превратиться
в столько же отложенных тиков. Хост не является планировщиком реального времени.

Долгий callback или `Tick` задерживает все следующие компоненты.
Потенциально длительную работу следует выносить из движкового потока
и возвращать в него готовый результат. Хост не делает этого автоматически
и не гарантирует отсутствие синхронного ввода-вывода: например,
Repository сохраняет конфигурацию из своего тика.
Внешний поток не должен напрямую вызывать JavaScript в общем контексте;
для передачи его завершений используется [JsExtLib.Post](JsExtLib.cs).

Исключение из `JsExtLib.Tick` или отдельного плагинного `Tick`
регистрируется через `Log.Fault`, после чего проход продолжается.
Ошибочный плагин остаётся в составе и получает следующий тик.
Это изоляция исключения, а не откат уже выполненной работы и не защита
от зависания: предельного времени выполнения отдельного плагина нет.

При включённом `/$YS/Performance` хост публикует среднюю и максимальную
длительность прохода (`Tick`, `TickMax`), интервал между началами проходов
(`Period`, `PeriodMax`) и максимальную измеренную длительность callback
JavaScript-таймера (`Script`); значения времени выражены в миллисекундах.
Обновление проверяется сначала примерно через 10 секунд, затем через
317 секунд, поэтому тоже может задержаться при занятом движке.
По умолчанию диагностика выключена. Эти метрики помогают различить
длительную работу и редкие пробуждения, но не измеряют сквозную задержку
от запроса пользователя до изменения интерфейса.

**Реализация.** [Program.PrThread, Tick](Program.cs);
[JsExtLib.Post, Tick, TakeMaxCallbackMs](JsExtLib.cs);
[Repo.Tick](Repository/Repo.cs).

**Проверки.** В [RepoTickTests](../Tests/Repository/RepoTickTests.cs)
есть проверки согласованного пакета
(`Tick_AppliesEverythingBeforePublishingAnything`) и отложенной команды
из подписчика (`DoCmd_QueuedWhilePublishingWaitsForTheNextTick`).
Они относятся к внутреннему контракту Repository.
[RepoTestBase](../Tests/Repository/RepoTestBase.cs) вызывает его тик вручную
и не запускает `Program`: эти тесты не проверяют межплагинный порядок,
период таймера, продолжение после ошибки плагина или метрики хоста.
Отдельных автоматических проверок этих свойств хоста нет.

## Остановка и отказ запуска

**Задача.** Освободить ресурсы затронутых плагинов в обратном порядке,
включая случай, когда запуск оборвался посередине.

**Контракт.** При штатной остановке `Program.Stop` помечает завершение
и будит движковый поток. Поток выходит из цикла, прекращает периодические
пробуждения и вызывает `StopPlugins`. Поскольку условие выхода проверяется
в конце прохода, после запроса остановки ещё может выполниться проход движка.
Повторные или конкурирующие вызовы `Program.Stop` не начинают вторую очистку.

Для каждого плагина учитывается достигнутый этап, причём вход в `Init`
или `Start` отмечается **до** вызова. В обратном порядке останавливаются
все, для кого уже начался `Init`: успешно запущенные, инициализированные
без `Start` и сам плагин, выбросивший исключение на незавершённом этапе.
Отключённые плагины и те, до чьего `Init` очередь не дошла, `Stop` не получают.
Это один механизм и для обычного завершения, и для перехваченного
отказа запуска.

Например, при ошибке `Start` одного компонента последующие компоненты
уже прошли `Init`, хотя их `Start` ещё не вызывался; их ресурсы тоже
должны быть освобождены. Поэтому `Stop` плагина не вправе предполагать,
что `Init` или `Start` завершились полностью.

Каждое исключение из плагинного `Stop` записывается вместе с достигнутым
этапом; оно не отменяет попытки остановить остальные плагины.
В штатном пути после завершения движкового потока хост освобождает
собственную подписку диагностики, таймер, обработчики процесса и объекты
синхронизации, затем контейнер MEF и журнал. Контейнер уничтожается после
плагинных `Stop`, чтобы освобождение его частей не опередило их завершение.

**Границы и ошибки.** На ожидание движкового потока, включая его `StopPlugins`,
отводится 20 секунд. При превышении хост пишет ошибку и вызывает
`Thread.Abort`: поток не фоновый и иначе мог бы удерживать процесс.
Эти 20 секунд — предел ожидания потока, а не гарантия общей длительности
выхода. Принудительное прерывание может попасть в сохранение или закрытие
базы; после него нельзя обещать полноценное освобождение ресурсов
или сохранность всех последних изменений.

`Stop` не является общей транзакцией и не обещает опустошить все очереди
системы. Ошибка очистки плагина может оставить его ресурсы занятыми;
обратный порядок лишь даёт остальным возможность завершиться.
Правила сохранения остаются у [Repository](#формат-xst) и
[PersistentStorage](../plugins/PersistentStorage/PersistentStorage.md).
В частности, `Repo.Stop` не перезаписывает конфигурацию, если её загрузка
не дошла до успешного завершения.

**Реализация.** [Program.Stop, PrThread, StopPlugins, PlugState](Program.cs);
[HAServer.OnStop](HAServer.cs); [IPlugModul](IPlugModul.cs);
[Repo.Stop](Repository/Repo.cs).

**Проверки.** Автоматических тестов обратного порядка остановки,
частичного `Init`/`Start`, ошибки `Stop`, конкурирующих запросов завершения
и принудительного прерывания в текущем наборе нет.
Наличие тестов Repository или журнала не подтверждает завершение
всего процесса: для этого нужны отдельные проверки жизненного цикла хоста.

## Общая модель: топики

Топик — адресуемый элемент общего дерева Repository:

| Свойство | Смысл |
|---|---|
| Имя | Имя относительно родителя, например `Sensor`. |
| Путь | Полный адрес, например `/dev/node/Sensor`. |
| State | Состояние: число, строка, объект или другое значение `JSValue`. Поля объекта State сами по себе не являются топиками. |
| Manifest | Манифест: атрибуты, тип, конфигурация и описание топика. |
| Дети | Непосредственные дочерние топики. |
| Потомки | Все топики ниже данного узла, включая детей и их поддеревья. |

Описание типа также является топиком, обычно под `/$YS/TYPES`.
Связь описания с экземпляром и содержимое его State разобраны
в [справочнике полей Topic](Repository/TopicFields.md#описания-типов).

Плагины описывают свои данные в этих терминах. XST ниже — только способ
сохранения и переноса дерева, не отдельная модель устройств или программ.
Подробности изменений и подписок: [Repository](Repository/Repository.md).

## Формат XST

XST хранит поддерево Repository в XML. Один XML-элемент соответствует одному
топику; State и Manifest записываются JSON-строками в атрибутах.
Формат используется для конфигурации, экспорта/импорта поддеревьев
и доставки описаний типов. Реализация: [Xst.cs](Repository/Xst.cs).
Выбор и установка пакетов из каталога относятся к
[WebUI](../plugins/WebUI/WebUI.md#каталог-типов).

### Соответствие дереву топиков

```xml
<xst path="/config">
  <i n="Demo" ver="1.0.0.0"
     s='{"value":42}'
     m='{"attr":4,"type":"Core/Object"}'>
    <i n="Enabled" s="true" m='{"attr":4}' />
  </i>
</xst>
```

Пример задаёт топик `/config/Demo` со State `{"value":42}` и Manifest
`{"attr":4,"type":"Core/Object"}`; при импорте версии добавляется поле
`version`. Его ребёнок `/config/Demo/Enabled` имеет State `true`.
Поле `value` в State не является ребёнком Demo.

| XML | Представление в Repository |
|---|---|
| `xst.path` | Путь корневого топика импортируемого поддерева. |
| `i.n` | Имя дочернего топика относительно родительского XML-элемента. |
| Вложенные `i` | Дети топика; дальнейшая вложенность задаёт остальных потомков. |
| `s` | State топика, сериализованный в JSON. |
| `m` | Manifest топика, сериализованный в JSON. |
| `ver` | Версия, ограничивающая применение элемента и его поддерева при импорте. |

Атрибуты `s`, `m`, `ver` допустимы как у `i`, так и у корневого `xst`.
Можно сохранить один топик непосредственно в корне, без дополнительного `i`:

```xml
<xst path="/config/Demo" ver="1.0.0.0"
     s='{"value":42}'
     m='{"attr":4,"type":"Core/Object"}' />
```

Явно переданный аргумент `path` метода Import имеет приоритет над `xst.path`.
Имена и регистр значимы: `Ai00` и `AI00` — разные дети.
Имя должно удовлетворять правилам [Topic](Repository/Topic.cs).

### JSON, экранирование и версии

State и Manifest сначала сериализуются как JSON (`\"`, `\n`),
затем экранируются для XML-атрибута (`&amp;`, `&lt;`, при необходимости `&apos;`).
Одинаково выглядящие поля разных уровней не смешиваются:
`m` — Manifest текущего топика; `manifest` внутри JSON из `s` —
обычное поле State, которому прикладной компонент может придавать смысл шаблона.

Корректный `ver` разбирается как `System.Version` и сохраняется в
`Manifest.version` с префиксом `¤VR`.
Если установленная версия не меньше импортируемой, пропускается весь элемент,
включая его детей. При отсутствии корректного `ver` этот ограничитель
не применяется. Версия в индексе каталога не заменяет серверную проверку:
правила индекса и обновления описаны в [WebUI](../plugins/WebUI/WebUI.md#каталог-типов).

Экспорт не выносит `Manifest.version` в XML-атрибут `ver`: поле остаётся
в JSON манифеста. Поэтому последующий импорт такого экспорта сам по себе
не включает проверку версий. Специальные значения JSON разбираются по
[общим правилам JsLib](#значения-jsvalue).

### Импорт, экспорт и конфигурация

XST переносит дерево, но не управляет периодичностью сохранения.
Загрузка при старте, отложенная запись, повтор после ошибки и защита
исходной конфигурации относятся к
[циклу Repository](Repository/Repository.md#конфигурация-и-перенос-поддеревьев).

#### Импорт поддерева

**Задача.** Подготовить переносимое описание поддерева до изменения
Repository, чтобы ошибка XML или адреса в применяемой части не оставила
частично созданную структуру.

**Контракт.** Файловый `Import` при пустом имени или отсутствующем файле
возвращает `false`; иначе открывает документ, передаёт его читающей форме
и после нормального возврата отвечает `true`.
Читающая форма сначала загружает XML целиком, определяет корневой путь
и строит план. Отсутствие пути и в аргументе, и в документе означает
выход без изменений, а не исключение.

При подготовке плана проверяются корневой путь и имена адресуемых `i`.
Элемент `i` без `n` пропускается вместе с поддеревом. Ветка, пропущенная
по версии, также не обходится для проверки имён её потомков.
До окончания подготовки плана новые топики не создаются.

Затем план применяется через
[Topic.Declare и Fill](Repository/Repository.md#дерево-и-структурные-операции).
Структура и содержимое становятся доступны непосредственно при заполнении,
а объявления `Created` идут через тик. Этот путь не создаёт обычные
`StateChanged`/`FieldChanged` на каждое импортированное значение.
Импорт не удаляет не упомянутых в документе детей существующего узла
и не является слиянием отдельных полей его Manifest.
Правила отсутствующего Manifest и State определяет `Fill`.

**Границы и ошибки.** Двухпроходность защищает от ошибок подготовки,
а не делает применение транзакцией с откатом.
Исключение во время `Apply`/`Fill` может оставить уже созданные
или изменённые узлы.

Некорректный JSON в `m` или `s` даёт предупреждение и не отменяет весь план.
Для существующего узла отсутствие подготовленного State оставляет прежнее
значение, но отсутствие Manifest не означает сохранение прежних полей.
Синтаксически допустимый JSON также не доказывает пригодность Manifest
для заполнения топика.

`true` файлового импорта означает завершение вызова, не обязательно
изменение дерева: документ мог не задать путь или целиком пропуститься
по версии. Оно также не подтверждает доставку событий подписчикам
или последующее сохранение импортированных данных.

**Реализация.** [Xst.Import, Prepare, Apply](Repository/Xst.cs);
[Topic.CheckPath, CheckName, Declare, Fill](Repository/Topic.cs).

**Проверки.** [TopicNameTests.CheckPath_BadSegmentThrows](../Tests/Repository/TopicNameTests.cs)
проверяет валидатор пути, а
[TopicTreeTests.Fill_SetsTheStateAtOnceAndAnnouncesTheTopic](../Tests/Repository/TopicTreeTests.cs) —
границу заполнения и события. Импорт используется для подготовки данных
в [LplcEditorTests](../Tests/WebUI/LplcEditorTests.cs), но это не тест
отказов самого XST. Прямых проверок пропуска по версии, ошибочного JSON,
отсутствующего пути и частичного применения при ошибке `Fill` нет.

#### Экспорт поддерева

**Задача.** Сериализовать выбранное поддерево и, при записи в файл,
не уничтожать прежний документ до подготовки нового.

**Контракт.** Входы — топик, назначение (поток или имя файла) и `configOnly`.
Корень документа соответствует выбранному топику и сохраняется всегда.
При `configOnly` из потомков остаются топики режима Config и необходимые
для их путей предки; полный режим включает всё выбранное поддерево.
Manifest записывается для включённых узлов. State записывается для Config,
а при полном экспорте — также для DB, если значение существует.
Временные State остальных режимов полный экспорт не сохраняет.

Потоковая форма пишет XML в переданный поток и вызывает `Flush`.
Файловая форма сначала записывает и закрывает `filename.tmp`,
затем заменяет существующий файл через `File.Replace` или переносит
в новый через `File.Move`. До этой подмены целевой файл не трогается.
При ошибке выполняется попытка удалить временный файл, исходное исключение
выходит к вызывающему коду; ошибка очистки отдельно журналируется.

**Границы и ошибки.** Файловая подмена не является обещанием аппаратного
сброса данных при отключении питания; на произвольный переданный поток
гарантия подмены файла вообще не распространяется.
Экспорт сам не применяет ожидающие команды Repository и не фиксирует
атомарный снимок всего дерева относительно параллельных изменений.
Одновременные экспорты в один файл должны исключаться вызывающим слоем:
имя временного файла общее, собственной сериализации таких вызовов нет.

Это перенос выбранной части модели, а не резервная копия всей системы:
архивные ряды, журналы и состояние исполнения плагинов в XST не входят.
Повторы записи выполняет цикл Repository, не сам `Xst.Export`.

**Реализация.** [Xst.Export, BuildExportDocument, Swap](Repository/Xst.cs).

**Проверки.** Прямых тестов отбора `configOnly`, наличия State разных режимов,
подмены существующего файла и отказа записи/подмены нет.
[RepoTickTests.Start_DoesNotSaveBeforeTheDelay](../Tests/Repository/RepoTickTests.cs)
проверяет только отсрочку в вызывающем Repository, не эти гарантии экспорта.

## Значения JSValue

**Задача.** Дать компонентам общие правила чтения и подготовки State,
Manifest и аргументов, не смешивая отсутствие значения с допустимым
значением другого типа.

**Контракт.** `JsLib` работает с переданными значениями NiL.JS, а не с очередью
Repository. Чтение поля, построение нового объекта или разбор JSON сами
по себе не меняют топик и не публикуют события.

- Читатели `AsBool`, `AsString`, `AsInt`, `AsDouble` принимают ожидаемый тип,
  а при неподходящем значении возвращают заданный вызывающим кодом default.
  Например, строка `"21"` не становится числом. `AsDouble` также отклоняет
  `NaN`, но не бесконечность; прикладные диапазоны должен проверять потребитель.
- `IsObject` отличает индексируемый объект от `JSValue.Null`, у которого
  объектный тип, но нет содержимого. `Field` читает путь с разделителем `.`,
  пропуская пустые сегменты; отсутствующая ветвь даёт `NotExists`.
  Пустой путь означает само значение, а не отдельное поле.
- `SetField` возвращает новую цепочку объектов вдоль пути, сохраняя
  ссылки на незатронутые ветви. Для пути к полю запись C# `null`
  или `JSValue.Null` удаляет конечное поле; пустой путь заменяет всё значение.
  Это не глубокая копия и не вызов `Topic.SetField`.
- `Clone` рекурсивно копирует перечисляемое содержимое объектов и массивов,
  оставляя массив массивом. Циклическая ветвь заменяется на `null`
  с предупреждением; это не средство сохранения произвольного графа объектов.
  `SameValue` использует сравнение NiL.JS, а `Equal` требует одинакового
  `ValueType` и отдельно сравнивает даты по времени. Эти операции не являются
  универсальным глубоким сравнением JSON; `ByteArray` сравнивается по байтам
  через собственный `Equals`.

Для обмена используются `ParseJson` и `Stringify`. Разбор знает два
специальных представления: строка с префиксом `¤BA` превращается в `ByteArray`
из Base64, а распознанная ISO-метка времени с миллисекундами —
в дату с местным временем. Год 1001 в такой метке означает запрос
текущего времени сервера. Эти строки нельзя считать обычным текстом,
который при разборе обязательно останется строкой.

**Границы и ошибки.** Default типизированного читателя — выбор вызывающего
кода, а не подтверждение корректности входа; сам читатель не сообщает об ошибке.
Некорректный JSON выбрасывает исключение. Ошибочная Base64-строка после `¤BA`
даёт предупреждение и пустой `ByteArray`; строка формы даты с недопустимой
датой сохраняется как текст с предупреждением. Успешный разбор поэтому
не равен полной проверке данных. Семантика полей остаётся в
[справочнике Topic](Repository/TopicFields.md), а правила применения —
в [Repository](Repository/Repository.md#очередь-изменений-и-тик-repository).

**Реализация.** [JsLib.Field, SetField, Clone, SameValue, Equal, ParseJson](JsLib.cs);
[ByteArray.toJSON, Equals](JsLib.cs).

**Проверки.** [TopicStateFieldTests](../Tests/Repository/TopicStateFieldTests.cs)
проверяют отсутствие события при повторном числовом State
(`SetState_RepeatedValueIsNotAnEvent`), чтение отсутствующего поля
(`GetField_OfAMissingFieldIsUndefined`) и сохранность прежнего Manifest
(`SetField_ReplacesTheManifestInsteadOfMutatingIt`) на уровне Repository.
Это не отдельный набор тестов `JsLib`: циклы при клонировании, специальные
JSON-строки и вся матрица типов/default напрямую не проверены.

## Применение конфигурации

**Задача.** Один раз применить настройку компонента при подключении
и поддерживать её рабочее значение после изменений топика.

**Контракт.** `JsExtLib.EnsureCfg` получает владельца, относительный путь,
тип ожидаемого значения, атрибуты, default и обработчик `apply`.
Если State уже имеет ожидаемый тип, используются его значение и существующие
атрибуты. Иначе для топика задаются переданные атрибуты и ставится в очередь
запись default. Это относится и к существующему топику с неверным типом,
а не только к новому.

`apply` вызывается до возврата из `EnsureCfg`, затем создаётся подписка
на значение этого топика. При начальной подстановке обработчик уже получает
default, хотя его запись в Repository ещё ожидает тика.
Результат метода — `SubRec`, который вызывающий компонент обязан освободить.
Снимок и подтверждение подписки также могут повторно вызвать обработчик:
`apply` должен допускать повторное применение того же значения.

**Границы и ошибки.** Это не схема валидации всех будущих записей:
последующие события читают State через `As<T>` без повторной подстановки default.
Ошибки первоначального `apply` выходят к вызывающему коду; ошибки при доставке
подписки обрабатывает Repository. Изменения топика при этом не откатываются.
Освобождение подписки снимает регистрацию, но не удаляет настройку
и не служит барьером для уже подготовленной доставки.
Механизм не запускает и не останавливает сам плагин.

**Реализация.** [JsExtLib.EnsureCfg](JsExtLib.cs);
[Topic.Subscribe](Repository/Topic.cs), [SubRec.Dispose](Repository/SubRec.cs).
Порядок доставки — в [механизме подписок](Repository/Repository.md#подписки).

**Проверки.** В [MqttSnConfigTests](../Tests/MQTT_SN/MqttSnConfigTests.cs)
`ExistingFlagsAreRecreatedAsConfigWithTheirValues` проверяет применение
настроек до первого тика, а `SettingsStayLiveUntilStopAndAreReappliedOnRestart` —
последующие изменения, освобождение подписок и повторное подключение
на конкретном потребителе MQTT_SN. Отдельных тестов всего контракта
`EnsureCfg`, ошибок `apply` и последующей смены типа State нет.

## Среда JavaScript

Общая среда предоставляет контекст NiL.JS, таймеры и адаптеры серверных
операций. Создание экземпляра блока, `Calculate`, доступ к топикам и время
жизни контекста блока относятся к
[Logram](../plugins/Logram/Logram.md#поддержка-javascript), а не к `JsExtLib`.

### Контекст и таймеры

**Задача.** Выполнять отложенные JavaScript-вызовы в серверном контексте
на движковом потоке.

**Контракт.** Хост [активирует контекст до запуска плагинов](#платформа-и-запуск).
Фоновый код передаёт готовое действие через `Post`; оно исполняется
из очереди завершений в `JsExtLib.Tick`. Затем обрабатываются таймеры.
Место этой работы в цикле хоста определено в
[проходе движка](#проход-движка).

Таймер принимает функцию и возвращает числовой идентификатор:
одноразовый задаёт задержку в миллисекундах, интервальный — повторение,
а `setAlarm` — ежедневное местное время суток из JavaScript Date.
Дата календарного дня у alarm не задаёт одноразовое событие.
Отрицательная задержка приводится к нулю; регистрация сама не вызывает
функцию, её исполняет механизм тика.

Повторный интервал отсчитывается от времени текущей обработки,
а не от фиксированной сетки прошедших сроков. Глобальный `setInterval`
приводит неположительный период к 1 мс; обёртки Logram передают период
в `SetTimer` напрямую и имеют свои
[ограничения повторения](../plugins/Logram/Logram.md#поддержка-javascript).
Поэтому одинаковое имя функции не означает полностью одинаковый контракт
во всех контекстах.

`clearTimeout` и `clearInterval` отменяют по идентификатору.
Серверный владелец может отменить все таймеры заданного контекста через
`ClearTimeout(Context)`. Отмена из выполняющегося callback запрещает
его дальнейшее повторение, но не прерывает уже начатый вызов.

**Границы и ошибки.** Исключение из действия очереди или callback таймера
журналируется через `Log.Fault`, остальные элементы продолжают обрабатываться.
Само исключение не отменяет интервальный таймер. Ограничителя длительности
JavaScript нет; таймеры существуют только в памяти, а расписание зависит
от местных часов и загрузки движка.
Значение, не являющееся функцией, может дать идентификатор `-1` без сообщения;
неверный тип аргумента `setAlarm` вызывает исключение.

`Post` — явный способ передачи работы, а не общее правило продолжений
любой асинхронной операции NiL.JS. Отмена таймеров контекста также
не отменяет его HTTP-запросы или чтение архива.

**Реализация.** [JsExtLib.ActivateEngineOnThisThread, Post, SetTimer, ClearTimeout, Tick](JsExtLib.cs).

**Проверки.** Отдельных тестов расписания, самоуничтожения таймера,
отмены по контексту, обработки исключений и передачи действий между потоками
в текущем наборе нет. Активация NiL.JS в
[RepoTestBase](../Tests/Repository/RepoTestBase.cs) лишь готовит среду тестов,
но не проверяет серверный цикл JavaScript.

### Внешние операции JavaScript

**Задача.** Предоставить скрипту ограниченный набор серверных операций,
явно различая запуск работы, получение результата и запись данных.

**Контракт.**

| Средство | Выполнение и результат |
|---|---|
| `XMLHttpRequest` | `open` поддерживает только асинхронный режим. Ответ и его тело читаются в фоне; готовые статус и текст передаются через `Post`, после чего вызывается `onreadystatechange`. При наличии HTTP-ответа доставляются состояния 2 и 4, без него — 4 со статусом 0. Состояние 1 устанавливается непосредственно в `open`; состояния 3 нет. |
| `Arch.Query` | Преобразует аргументы и запускает зарегистрированного поставщика `AQuery` через `Task.Run`. Форма истории, допустимые аргументы и ошибки описаны у [Archivist](../plugins/Archivist/Archivist.md#входы-клиентов-и-ошибки); это не вызов HTTP API и не передача результата через `Post`. |
| `File.AppendText` | Синхронно дописывает текст, при необходимости создавая каталоги. Путь пересобирается относительно родителя рабочего каталога сервера; это не обычная передача произвольного пути в файловую систему. Пустые путь или данные пропускаются. Ошибки файловой операции журналируются, но скрипту не возвращается подтверждение записи. |
| `console` | Передаёт текст и уровень в [общий журнал](#доставка-сообщений); собственной истории у скрипта нет. Возврат из вызова ещё не подтверждает файловую запись. |

**Границы и ошибки.** Это не полный браузерный XMLHttpRequest:
`setRequestHeader` обрабатывает только `Content-Type`, а строковое тело
не отправляется для GET и HEAD. При HTTP-ошибке сохраняются фактический
статус и доступное тело ответа; сетевая ошибка без HTTP-ответа отличается
от HTTP-статуса ошибки. Исключения самого `onreadystatechange` журналируются.

Несмотря на асинхронное получение ответа, отправка строкового тела использует
синхронные `GetRequestStream` и запись в поток. Поэтому вызов `send`
может задержать движок или выбросить исключение ещё до фонового ожидания.
Так же синхронна запись через `File.AppendText`.
Эти средства не обещают полностью неблокирующего ввода-вывода
или автоматического возврата любых продолжений скрипта на движковый поток.

**Реализация.** [JsExtLib.XMLHttpRequest, AQueryJS, AppendFile, LogWriter](JsExtLib.cs).

**Проверки.** Прямых тестов XMLHttpRequest, его состояний и HTTP-ошибок,
записи файлов из скрипта и адаптера `Arch.Query` нет.
Проверки общего журнала не проверяют мост `console` из NiL.JS.

## RPC

**Задача.** Связать именованное серверное действие с обработчиком,
не привязывая общий реестр к транспорту или интерфейсу.

**Контракт.** `RPC.Register` добавляет обработчик в единое пространство имён.
Одинаковое имя нельзя зарегистрировать повторно, в том числе через другую
форму регистрации: возникает исключение, прежний обработчик сохраняется.
Объявление действия в Manifest и его регистрация — разные операции;
содержимое [описания Action](Repository/TopicFields.md#описание-действий)
само по себе не создаёт обработчик.

`RPC.Call` передаёт обработчику топик отдельно от аргумента `JSValue`;
C# `null` вместо аргумента заменяется на `undefined`.
Обработчик вызывается непосредственно в потоке вызывающего кода.
Варианты ответа:

- обработчик без функции ответа после нормального возврата автоматически
  отвечает `undefined`;
- обработчик с `reply` может ответить сразу или позднее, в том числе из
  другого потока; обёртка пропускает **не более одного** ответа на вызов.

Если имя не зарегистрировано, `Call` возвращает `false`, не вызывая ответ.
`true` означает, что обработчик найден и его вызов вернулся без исключения,
но не гарантирует завершение отложенной работы или уже полученный результат.

**Границы и ошибки.** «Не более одного ответа» не означает «ответ обязательно
придёт»: собственного тайм-аута и отмены RPC нет. Синхронное исключение
обработчика или получателя ответа выходит к вызывающему коду; общий реестр
не превращает его в успешный ответ и не откатывает побочные эффекты.
Ошибки отложенной работы должен передать сам обработчик.

Потокобезопасность реестра не сериализует вызовы обработчиков и не переносит
их или ответы на движковый поток. Проверки доступа, объявленного действия,
форма результата и предельное ожидание принадлежат вызывающему слою:
см. [действие и отложенный ответ WebUI](../plugins/WebUI/WebUI.md#действие-и-отложенный-ответ).
Регистрации живут в статическом реестре процесса; снятия регистрации
или автоматической замены обработчика при остановке плагина нет.

**Реализация.** [RPC.Register, Call](Rpc.cs).

**Проверки.** В [LplcEditorTests](../Tests/WebUI/LplcEditorTests.cs)
`Actions_DeclaredHandlerReceivesProgramAndArguments` проверяет через WebUI
передачу топика и аргумента, немедленный и отложенный ответ и отсутствие
второго результата. `Actions_RejectUndeclaredNamesAndReportMissingHandlers`
различает необъявленное действие и отсутствие зарегистрированного обработчика.
Это проверки всего пути WebUI, а не изолированное доказательство защиты RPC
от конкурентных ответов. Прямых тестов такой гонки, повторной регистрации
и выхода исключений из обработчика нет.

## Журналирование и диагностика

### Доставка сообщений

**Задача.** Принимать диагностику из разных потоков, не выполняя файловую
запись и рассылку подписчикам в каждом производителе сообщения.

**Контракт.** Вызовы `Log.Debug`, `Info`, `Warning`, `Error` и `OnWrite`
ставят в очередь уровень, местное время сервера, строку формата и аргументы.
Потребитель в ThreadPool форматирует сообщение и последовательно передаёт его
в доступные каналы: отладочный вывод, консоль, включённый файл,
подписки `Write` и `RecordWritten`.
Возврат из вызова означает постановку в очередь, а не доставку или сохранение.

Обработчики подписок вызываются отдельно, на потоке потребителя,
не на движковом потоке. Исключение одного обработчика сообщается напрямую
в доступные консоль/отладочный вывод и не мешает остальным получить запись.
Обратно в ту же очередь такая диагностика не направляется.
Связь живого сообщения с файловой записью определяет
[файловая история](#файловая-история-журнала).

**Границы и ошибки.** Медленный подписчик задерживает потребителя и следующие
сообщения; тайм-аута обработчика и ограничения размера очереди нет.
Некорректная строка формата превращается в запись Error с `Bad format`,
а недопустимый уровень отклоняется ещё при постановке в очередь.

`Log.Finish` запрашивает выпуск удержанных сбоев, будит потребителя,
снимает регистрацию ожидания и ждёт до 400 мс. Это необратимое завершение
журнала процесса, а не обещание, что к возврату вся очередь гарантированно
записана и сброшена на носитель. После него нельзя рассчитывать
на доставку новых сообщений.

**Реализация.** [Log.Enqueue, Process, Publish, PublishEntry, Close](Log.cs).

**Проверки.** В [LogFileHistoryTests](../Tests/LogFileHistoryTests.cs)
`LiveFileIdIsImmediatelyReadable` связывает живую запись с читаемым файлом,
`DisabledFileLoggingHasLiveOnlyEntriesAndNoHistory` проверяет работу без файла,
а `FileFailureIsReportedWithoutRecursiveLogging` — диагностику отказа записи.
Изоляция исключения подписчика, задержка потребителя и завершение с ещё
занятой очередью отдельными тестами не проверены.

### Ограничение повторяющихся сбоев

**Задача.** Не заполнять журнал одинаковым стеком исключения на каждом тике,
сохраняя сведения о количестве сбоев.

**Контракт.** `Log.Fault` группирует обращения по месту ошибки и короткому
имени типа исключения; `subject` и текст исключения не создают отдельный ключ.
Первое сообщение сразу ставится в очередь. Повторы в пределах окна
30 секунд удерживаются и учитываются в следующем сообщении той же группы.
Если серия затихла, потребитель сам выпускает её оставшийся хвост после окна,
даже без нового обращения к `Fault`. При смене даты формируется суточный итог.
Вызывающему компоненту не требуется отдельно вызывать сброс.

**Границы и ошибки.** Ограничение действует только на `Fault`, не на обычные
`Warning` или `Error`, и не ограничивает общий размер очереди.
Хвост не обязан появиться ровно через 30 секунд: он зависит от пробуждения
и занятости потребителя. Это сводка количества и последней ошибки,
а не сохранение текста каждого подавленного сообщения.

**Реализация.** [Log.ReportFault, FlushFaults, SummariseFaults, EmitFault](Log.cs).

**Проверки.** [LogFaultTests](../Tests/LogFaultTests.cs):
`TheDayTotalIsWrittenOutWhenTheDateTurnsOver` проверяет суточное количество,
`AHeldTailSurvivesTheDayTurningOver` — удержанный хвост через полночь,
`TheConsumerWritesTheTailByItself` — выпуск хвоста без внешнего сброса.
Они используют отдельный журнал с управляемыми часами и укороченным окном;
`LogFaultReachesTheProcessLog` отдельно проверяет общий API.
Это не нагрузочная проверка реального 30-секундного окна.

### Файловая история журнала

**Задача.** Читать ранее записанные сообщения из тех же файлов, в которые
пишет сервер, без второй копии в LiteDB и без зависимости от PersistentStorage.

**Контракт.** Новые файлы в каталоге `../log` называются только датой:
`yyyyMMdd.log`. Формат — UTF-8 без BOM, местное время сервера с миллисекундами
без часового пояса. Заголовок содержит версию, дату и идентификатор экземпляра файла:

```text
# EnviriotLog v2 date=2026-11-11 fileId=0123456789abcdef0123456789abcdef
08:57:12.345 [I] Подключение установлено

08:57:13.007 [E] Ошибка чтения
| System.IO.IOException: соединение закрыто
| Дополнительные сведения

```

Первая строка содержит время, уровень и начало сообщения. Продолжения получают
префикс `| `, пустая физическая строка завершает запись. Переносы сообщений
нормализуются в LF; пустые строки, отступы и собственные `| ` сохраняются.
Старый текстовый формат не читается, не конвертируется и не удаляется
новой ротацией. Файл с новым именем, но чужим заголовком не перезаписывается.

`Log.ReadHistory(beforeId, count)` возвращает до 200 записей в порядке
«дата файла, затем позиция», от старых к новым внутри выданной страницы.
Без `beforeId` читается конец истории, с ним — записи строго перед заданной.
Пустой результат означает конец; при полной последней странице допустим
дополнительный пустой запрос. Отдельного `cursor` нет.

`id` записи объединяет дату, `fileId` и байтовую позицию начала.
Идентификатор не зависит от timestamp или текста, поэтому одинаковые
сообщения в одну миллисекунду не теряются. Один ID используется и в истории,
и в `Log.RecordWritten`. Он публикуется после видимости полной записи
файловому читателю; это не гарантия аппаратного сброса на носитель.
У живого сообщения без подтверждённой файловой записи `id=null`.
Прежний `Log.Write` остаётся доступен подписчикам без файловых ID.

Читатель использует блоки и фиксирует длину файла для запроса, не загружая
весь журнал в память. Неполный хвост текущего суточного файла не выдаётся
как завершённая запись. Ротация удаляет только файлы нового формата,
которые по времени последней записи старше 36 суток относительно настоящих
часов. Вымышленные часы тестовых сообщений не определяют возраст файлов.

**Границы и ошибки.** Время — показание часов сервера, не UTC-момент:
его нельзя автоматически пересчитывать по часовому поясу браузера.
Перевод часов назад не переставляет записи внутри файла.
История включает Debug; скрытие уровней принадлежит интерфейсу.
При `Log.UseFile=false` история недоступна, даже если файлы существуют,
но живой поток продолжает работать.

Неверный или устаревший `beforeId`, отказ доступа и повреждённый новый формат
дают ошибку, а не успешную пустую страницу. Ошибки файловой записи сообщаются
напрямую, без возвращения ошибки в очередь неисправного файла.
Файлы журнала не включаются в резервные копии PersistentStorage.
Прежняя коллекция LiteDB `history` удаляется при его успешном `Init`
после стартовой копии, без переноса сообщений.

**Реализация.** [Log.ReadHistory, RecordWritten](Log.cs);
[FileLogHistory.Append, Read, Prune](FileLogHistory.cs).
Потребитель и догрузка пропусков описаны в
[WebUI](../plugins/WebUI/WebUI.md#история-и-живой-журнал).

**Проверки.** [LogFileHistoryTests](../Tests/LogFileHistoryTests.cs) проверяют
формат, UTF-8, страницы с одинаковым временем, конкурентную запись,
ротацию, повреждения, файловые ID живого потока и ограниченный объём чтения
большого файла. Существующие [LogFaultTests](../Tests/LogFaultTests.cs)
проверяют ограничения повторяющихся сбоев. Удаление только старой коллекции
проверяет [HistoryRemovalTests](../Tests/PersistentStorage/HistoryRemovalTests.cs)
на временной базе. Эти проверки не моделируют аппаратное отключение питания.
