# LPLC

LPLC — серверная модель и компилятор диаграмм LogramPLC (`pa1`).
Код находится в пространстве имён `X13.LogramPLC` и входит в сборку
[MQTT_SN](../MQTT_SN.csproj).

Папка содержит независимое от Repository ядро диаграммы, адаптер дерева топиков,
синхронизацию схемы для редактора и встроенные типы блоков. Она не содержит
браузерный редактор, реализацию VM прошивки или транспорт загрузки.
Байткод генерирует [DPLC](../DPLC/DPLC.md), загрузкой управляет
[DevicePLC](../DevicePLC.cs), UI реализован в [WebUI](../../WebUI/Views/Lplc)
и [logram-document.js](../../../Output/www/ide/components/logram-document.js).

## Конвейер и границы слоёв

```text
топик программы pa1 и M-переменные устройства
  → LP_Tree.Read
  → LP_Diagram
  → LP_DiagramBinder
  → LP_DiagramGenerator: JS + карта строк
  → LP_DiagramCompiler / EP_Compiler
  → Hex, StackBottom, Elements, Variables, Problems, Warnings
  → LP_Program / DevicePLC: привязка и загрузка
```

`LP_DiagramCompiler` одноразовый: одна диаграмма — один Compile.
Он возвращает общий результат и сведения по элементам; экземпляр EP_Compiler
с AST после компиляции не удерживается. Проблемы связывания останавливают
генерацию; ошибки DPLC переводятся из координат JS в координаты диаграммы.

Binder подменяет имена элементов внутренними именами (`_cN`, `_bN`, `_pN`,
`_vN`), чтобы названия топиков не конфликтовали с именами режимов и API.
Блоки-выражения используют поля общего объекта `_x`, а не отдельный класс
на каждую операцию.

Порядки инициализации и исполнения различаются:

- Конструктор поставщика ресурса выполняется до потребителей; отсутствующая
  зависимость или цикл зависимостей конструкторов — ошибка компиляции.
- В Tick источник располагается до потребителя, ничьи разрешаются порядком
  диаграммы. В циклической связи первый блок читает сохранённые поля тех блоков,
  которые ещё не исполнились в текущем цикле.
- Чтение из дерева сохраняет порядок детей; одинаковая модель должна давать
  воспроизводимый байткод.

Присваивания переменным-приёмникам добавляются после соответствующего блока.
Сгенерированное объявление переменной не задаёт начальное значение, чтобы Start
не затирал уставку, уже записанную шлюзом в меркер.

## Представление в Repository

Программа определяется типом `Ext/LogramPLC`, а не только именем `pa1`.
По этому типу её находят наблюдатели и WebUI.
Блоки — дочерние топики программы; переменные — дочерние M-топики устройства,
то есть соседи `pa1`, а не его дети.
У `pa1` нет самостоятельных переменных аппаратных входов/выходов,
`Ta*`/`Sa*` и suppressed. Периферию обслуживают блоки и API программы,
а её доступность ограничивают `AvailablePins`/`AvailableUarts`.
Поля `LPLC.in`/`LPLC.out` ниже описывают **пины диаграммы**,
а не отсутствующие I/O-объекты устройства.

| Данные | Где находятся и что означают |
|---|---|
| `type` блока | `LPLC/*`; определяет источник кода/выражения и схему. |
| State Func/SerialPort | Тело Tick с входами A..H; не полный класс. |
| State переменной | Значение, синхронизируемое с меркером устройства. |
| `LPLC.pos` | Положение элемента, не исходный код программы. |
| `LPLC.args` экземпляра | Сохранённые настройки конструктора, включая настройки только времени компиляции. |
| `LPLC.in` экземпляра | Видимые входы и их источники: связь, переменная или константа. |
| `LPLC.out` экземпляра | Показанные выходы; полный каталог выходов берётся из `mi`. |
| `LPLC.run` блока | Видимый пустой объект со скрытым неперечислимым результатом компиляции. |
| `LPLC.loaded` программы | Сохранённый отпечаток последней подтверждённой загрузки. |
| `LPLC.modified` программы | Вычисляемое сравнение с загрузкой: true, false либо отсутствие значения. |

Источники входов в [LP_Tree](LP_Tree.cs):

- строка `Block.Output` — выход блока той же программы;
- строка без точки — переменная устройства;
- число или Boolean — константа;
- `LPLC.in.x` переменной делает её приёмником.

Поддерживаемые переменные соответствуют тегам `Mz`, `Mb`, `MB`, `Mw`, `MW`,
`Md`, `Mf`. Префикс без адреса обозначает ещё не привязанную переменную:
[MsDevice](../MsDevice.cs) не регистрирует такой тег на устройстве.
Run назначает полный тег по результату компиляции.

Результат в `LPLC.run` не сериализуется в базу/XST. Изменение соседних
`LPLC.pos` или `LPLC.in.*` само по себе не удаляет скрытый объект, но перезагрузка
из базы или замена `LPLC`/`LPLC.run` его теряет. Это кэш, а не сохраняемый
источник программы.

## Типы блоков и контракт конструкторов

[LPLC.xst](LPLC.xst) встроен в сборку под именем `X13.LogramPLC.LPLC.xst`.
`LP_Tree.ImportTypes` восстанавливает встроенные топики типов до открытия шлюзов.
Правила применения версий и файлового представления дерева описаны в
[Server.md](../../../Server/Server.md#формат-xst).

### Топики типов и экземпляров LogramPLC

[catalog/LPLC](https://enviriot.github.io/catalog/LPLC/) дополняет встроенные
блоки. В нём находятся, например,
[описание HDC1080](https://enviriot.github.io/catalog/LPLC/TWI/HDC1080.xst)
и [описание BME280](https://enviriot.github.io/catalog/LPLC/TWI/BME280.xst).
TwiMaster и SCAN_BUS входят во встроенные топики типов;
установка драйвера датчика не заменяет настройку мастера шины.

Тип блока — потомок `/$YS/TYPES/LPLC`, например ребёнок ветви TWI
с именем HDC1080 и путём `/$YS/TYPES/LPLC/TWI/HDC1080`.
Его Manifest содержит атрибуты и версию описания, а State — код, схемы
и шаблон Manifest будущего экземпляра.
Работа с внешним каталогом описана в [WebUI](../../WebUI/WebUI.md#каталог-типов).

Экземпляр блока — ребёнок программы, например `/dev/node1/pa1/HDC1080_1`.
Он имеет собственный Manifest с `type = LPLC/TWI/HDC1080`,
сохранёнными аргументами, связями и положением.
Код обычного класса берётся из State топика типа, а не из State экземпляра;
исключение Func/SerialPort с телом Tick рассмотрено ниже.
Пины и аргументы — поля данных, не дочерние топики блока.

Поля **State топика типа**:

| Поле | Контракт |
|---|---|
| `hint`, `icon`, `willful` | Описание, пиктограмма и метаданные создания элемента. |
| `LPLC.src` | Полный класс с constructor и Tick, который компилируется в байткод. Это не серверный `src` из каталога ServerTWI. |
| `LPLC.args` | Массив имён аргументов в порядке конструктора. |
| `LPLC.in` | Массив имён аргументов Tick; для этих автономно опрашиваемых датчиков пуст. |
| `manifest.type` | Тип экземпляра, например `LPLC/TWI/HDC1080`. |
| `manifest.MQTT-SN.tag` | `---`: сам блок не является регистрируемым объектом устройства. |
| `manifest.LPLC.args` | Сохранённые настройки экземпляра и их начальные значения. |
| `manifest.LPLC.in`, `manifest.LPLC.out` | Начальные входы/связи и показанные выходы. |
| `manifest.LPLC.pos`, `manifest.LPLC.run` | Начальное положение и пустой контейнер результатов компиляции. |
| `mi.LPLC.mi.args.mi` | Дескрипторы параметров: строки, подписи, редакторы, defaults, ограничения и источники вариантов. |
| `mi.LPLC.mi.in.mi`, `mi.LPLC.mi.out.mi` | Каталог доступных входов/выходов, описания и defaults их представления. |

Обычные блоки могут вместо `LPLC.src` использовать `LPLC.expr` или `LPLC.op`;
это альтернативные формы описания вычисления, читаемые `LP_Tree`.
Для классов поддержка языка определяется DPLC, а не возможностями полного
JavaScript на сервере.

Фрагмент состояния типа HDC1080; полный `LPLC.src`, пиктограмма и `mi`
находятся в [опубликованном описании](https://enviriot.github.io/catalog/LPLC/TWI/HDC1080.xst):

```json
{
  "LPLC": {
    "args": ["TwiNr", "Address", "Period"],
    "in": []
  },
  "manifest": {
    "type": "LPLC/TWI/HDC1080",
    "MQTT-SN": {"tag": "---"},
    "LPLC": {
      "pos": {"top": 0, "left": 0},
      "args": {"TwiNr": 0, "Address": 64, "Period": 30000},
      "in": {},
      "out": {"T": true, "H": true, "Valid": true},
      "run": {}
    }
  }
}
```

Это фрагмент State топика типа; код класса и часть метаданных опущены.
В его `mi` TwiNr выбирается через `choices.provider = bus`,
`kind = twi`, `scope = configured`; Address — через список `[64]`
с форматом `0x{0:X2}`; Period — через список `[1000, 30000, 300000]`
и отображение `{0} ms`.
У BME280 тот же порядок аргументов, default Address 118 и дополнительный выход P.

Каталог выходов и показанные выходы различаются: Status описан в `mi`,
но отсутствует в начальном `manifest.LPLC.out` HDC1080.
Значения выходов — поля экземпляра класса (T/H/Valid/Status),
а не дочерние топики, создаваемые через серверный SetState.

Актуальные State.LPLC.src типов HDC1080/BME280 используют PrintF.
Для их исполнения нужна прошивка с поддержкой этого API.
Контракт описан в [DPLC](../DPLC/DPLC.md#потоковые-api-и-printf).

### Контракт типа и экземпляра

Тип и экземпляр используют похожие имена полей с разным назначением:

- `State.LPLC.args` **топика типа** — массив имён параметров в порядке вызова конструктора.
- `Manifest.LPLC.args` **экземпляра** — объект сохранённых значений; его набор полей
  может отличаться от массива параметров.
- `State.LPLC.in` типа описывает входы Tick; аргументы конструктора не становятся
  от этого подключаемыми входами.
- Исходник обычного каталогового класса хранится в `State.LPLC.src` типа,
  а исходник Func/SerialPort — в State экземпляра.

Аргументы — конечные числовые/Boolean-литералы либо константы описания устройства.
Их схема находится в `mi.LPLC.mi.args.mi.<name>`:
`cdr`, `label`, `editor`, `format`, `readonly`, `required`, границы, `choices`, `derive`.
Разбор и разрешение используют общие
[ConstructorSchema](../../../Server/Plc/ConstructorSchema.cs) и
[ConstructorResolver](../../../Server/Plc/ConstructorResolver.cs).

### Порядок и оформление

- `cdr`: 1-based строка отображения, 0 скрывает параметр; диапазон 0..255.
- Неуказанные позиции идут после явных в порядке конструктора.
  Настройкам, которые не передаются в конструктор, нужна явная позиция.
- Порядок отображения не меняет порядок вызова; вычисленные значения не сохраняются.
- Без дескрипторов сохраняется прежнее поведение конструкторов.
- Composite format поддерживает `{0}`, выравнивание до 256 символов,
  форматы `D`, `X`, `F`, `E`, `G` в обоих регистрах и точность до 16.
  Поддерживаются экранированные фигурные скобки.
- Неподдерживаемый формат даёт диагностику и буквальное отображение.
  Подписи/отображаемый текст ограничены 256 символами; алиасы пинов остаются текстом.

Defaults применяются при создании, а не исправляют ошибочные/пропущенные
сохранённые значения во время компиляции. Ограничения типа имеют приоритет
над метаданными отображения экземпляра.

### Выбор и зависимости

`choices.provider`:

- `list` — типизированные `values`;
- `pin` — режим либо `kind`/`busArg`/`role`;
- `bus` — `kind` и `scope`: `supported` или `configured`;
- `bus-option` — именованные значения опции выбранной роли шины.

`configured` означает наличие корректного поставщика ресурса в той же программе.
Тип объявляет его, например, через
`LPLC.provides: [{kind:"twi",numberArg:"TwiNr"}]`.
`derive.provider: "bus-mode"` получает режим из kind/busArg/role.
`option` с провайдером `bus-option` проверяет числовую опцию роли.

`allowNone: true` разрешает явное -1 (Disabled).
`excludeArgs` задаёт несколько взаимно исключаемых GPIO; старое `excludeArg`
также поддерживается. Вычисление режима может использовать `pinArg`:
для выключенного пина результат -1, иначе роль должна существовать.

Адрес TWI — обычный числовой список, например `values: [118,119]`
с `format: "0x{0:X2}"`, без обнаружения устройств и кэша адресов.
Неверные, отсутствующие и циклические зависимости не заменяются
«подходящим» значением автоматически.
Изменение аргументов требует пересборки/загрузки, а не меняет GPIO на лету.

## Специализированные блоки

### Func и Pin

Func получает тело Tick(A..H). `return` формирует Q; записываемые `this.X`
образуют дополнительные выходы. Разбор идёт по AST, а не поиском подстрок:
ссылки в комментариях и строках не являются выходами.
Отсутствие возвращаемого значения сохраняет Q через добавленное
`return this.Q`; неиспользуемые хвостовые входы не передаются в Tick.

Pin использует режим и GPIO из описания устройства. Режим `io` определяет
возможность чтения/записи; режимы без `io` относятся к конфигурации шин.
Ограничения типа дополнены отчётами устройства, описанными в
[DPLC](../DPLC/DPLC.md#отчёты-доступности-ресурсов).

### SerialPort

`LPLC/SerialPort` — Func с генерируемым конструктором UART.
Это не последовательный шлюз сервера из [MsGSerial.cs](../MsGSerial.cs).
Меню UART1/UART2, создание экземпляра и редактирование аргументов находятся
в [LplcPaletteBuilder](../../WebUI/Views/Lplc/LplcPaletteBuilder.cs)
и [LplcViewProvider](../../WebUI/Views/Lplc/LplcViewProvider.cs).

Настройки: Port, TX, RX, Baud, Frame, DE. Начальные значения — 9600, 8N1,
DE Disabled. TX/RX обязательны даже для передачи без приёма; произвольные GPIO
автоматически не назначаются. Корректные `defaultPin` применяются при создании.
DE включает RS-485 и должен отличаться от TX/RX.

Режимы/пины фильтруются по описанию устройства и AvailablePins/AvailableUarts.
Доступность Serial требует разных допустимых TX/RX, но не требует свободного DE.
В одной программе допускается один SerialPort на UART.
Генератор передаёт конструктору порт, пины, вычисленные режимы, скорость и формат;
TX настраивается с Baud, RX — с Format, включённый DE — с опцией 0.

State остаётся телом Tick; класс и конструктор в нём не объявляются.
Единственное служебное поле `this.Port` доступно только для чтения и как выход.
Редактор, связи, дополнительные выходы, Trace и modified используют
те же механизмы, что и Func.

Пример тела Tick:

```js
if(A) return PrintF(this.Port, "%5.1f", B);
return false;
```

При ненулевом A каждый Tick пытается записать B с одним знаком после точки
и шириной не меньше 5. Q означает принятие записи, не завершение передачи UART.
`SendByte(this.Port, value)` отправляет младший байт, включая 00/FF;
`PrintF(this.Port, "%d", value)` — знаковое целое текстом.
Полный контракт потоков и формата находится в
[DPLC](../DPLC/DPLC.md#потоковые-api-и-printf).

Последовательность нескольких вызовов может принять только начало сообщения:
повторы и состояние протокола задаёт Tick. CR/LF и прочие управляющие байты
передаются явно через SendByte. У блока нет дополнительной очереди сообщений,
снимка аргументов или фонового автомата передачи.

Пример ограниченного чтения:

```js
this.Read = 0;
for(let i = 0; i < 3; i++) {
  let b = UartGetByte(this.Port);
  if(b < 0) break;
  this.Sum = this.Sum + b;
  this.Read++;
}
```

`UartGetByte` возвращает 0..255 или -1; 00/FF — данные.
`UartBytesToRead` сообщает количество после паузы или заполнения половины
RX-буфера, а не при каждом байте. Выходы диаграммы видят итог Tick,
не отдельное событие на каждый байт. RX может работать при заполненном TX.
Независимые читатели одного RX-буфера и отправители одного UART требуют
согласования: SerialPort не реализует арбитраж транзакций.

### TWI Master

Меню TWI строится по полным парам `TWI<n>_SDA` / `TWI<n>_SCL`
из `PLC.groups` типа устройства. Оба режима должны быть configuration-only,
без `io`. Их `v` — значения прошивки; арифметической связи между ними нет.

Публичные имена и `TwiNr` нумеруются с нуля. Если описание содержит TWI0,
индексы сохраняются, иначе из индексов описания вычитается 1.
Пропуски сохраняются; отсутствующие шины не создаются.
Нумерация UART1/2 этим правилом не меняется.

Контракт TwiMaster:

```text
constructor(SdaPin, SdaMode, SclPin, SclMode)
Tick()
```

Конструктор вызывает `ConfigPin(pin, mode, 0)` для обоих пинов.
Нулевая опция использует значение прошивки по умолчанию.
Tick пуст, передачи данных мастер не выполняет.
Сохраняются и отображаются только `TwiNr`, `SdaPin`, `SclPin`;
режимы выводятся из выбранной шины, не редактируются и не сохраняются.
`TwiNr` нужен при компиляции, но не передаётся конструктору.

В программе допустим один мастер на шину. SDA/SCL должны различаться
и входить в группы соответствующих режимов.
`defaultPin` рядом с `v` может быть числом либо именем из `PLC.names`;
это не `opt.default`. Повторные группы должны согласовывать defaultPin.
Отсутствующие, конфликтующие или недопустимые defaults оставляют пин незаданным;
совпадающие SDA/SCL оставляют незаданными оба. До компиляции нужны корректные
назначения. Обновление типа не переназначает существующие экземпляры.

Старые экземпляры с one-based `TwiNr` требуют уменьшения значения на 1
либо пересоздания. Имена топиков можно изменить отдельно; переименование
само по себе не меняет шину. Автоматической миграции настроек нет.

### SCAN_BUS

`LPLC/TWI/SCAN_BUS` описан во встроенном каталоге по пути
`/$YS/TYPES/LPLC/TWI/SCAN_BUS`. Аргумент `TwiNr` zero-based, default 0;
в той же программе нужен корректный TwiMaster. Сканер не конфигурирует пины.
Компилятор отклоняет отсутствие мастера; для внешней прошивки обращение
к неоткрытой/некорректной шине соответствует ошибке `0x8A`.

Контракт входа/выхода:

- Фронт Scan запускает один проход адресов 0x08–0x77.
  Для повторного запуска нужен возврат в 0; удержание 1 не повторяет сканирование.
- Триггеры во время сканирования игнорируются. Tick получает аргументы
  по значению, поэтому внутренний one-shot не обнуляет источник связи
  или сохранённую константу входа.
- Addr содержит последний подтверждённый адрес либо -1 до первого результата.
  Только успешная проба меняет Addr; простой, ошибка, завершение и начало
  следующего прохода его не сбрасывают. Это не импульс и не список адресов.
- На каждый подтверждённый адрес формируется одна best-effort запись Info,
  например `TWI0 addr=118`, через PrintF API 26 / LOG_INFO.
  Запись явно завершается; при заполненном буфере целиком отбрасывается,
  без частичного префикса, блокировки или повтора.
- Idle/NACK/timeout/-1 не создают записей. Удержание Addr не повторяет журнал
  и не заполняет меню выбора адресов. Нужна прошивка с поддержкой PrintF.

Алгоритм использует API 40/41: `TwiBusControl(bus, address)` выполняет пробу
без данных записи/чтения, `TwiBusStatus` возвращает RDY (`0x1000`)
или timeout/NACK/bus-error (`0xE000`). Чтение конечного статуса закрывает
транзакцию. Опрос выполняется поэтапно, не более одного раза за Tick;
тайм-аут обеспечивает прошивка, неответившие адреса пропускаются.

На время сканирования нужен исключительный доступ к шине: другой драйвер/сканер
не должен читать её статус или начинать транзакцию параллельно.
Старые экземпляры с Start/Q требуют замены полей на Scan/Addr и перепривязки
связей либо пересоздания. Импорт каталога экземпляры не переписывает;
после миграции нужны Build/Run.

## Интеграция, статусы и диагностика

`LP_Schema.Watcher` создаётся плагином независимо от DevicePLC:
схема нужна и при offline-редактировании. Он обновляет каталог выходов
Func/SerialPort и шаблоны переменных. Некорректный редактируемый исходник
не стирает предыдущую схему выходов.

Build типизированного `pa1` работает без зарегистрированного устройства.
Браузер при открытии LPLC вызывает Build для текущего корня.
Build формирует результаты и сравнение, но не записывает загруженный отпечаток
и не назначает переменным сетевые адреса.

Run компилирует, обновляет шаблоны переменных и их теги, затем передаёт результат
загрузчику. [DevicePLC](../DevicePLC.cs) вызывает `MarkLoaded` после подтверждения
загрузки/запуска либо подтверждения совпадающих блоков уже исполняемой программы.
Start/Stop управляют исполнением без пересборки.

`LP_Status` хранит входные данные и отпечаток последней сборки отдельно
от `LPLC.loaded`. Исходник, связи, конфигурация и описание типа влияют
на сравнение; положение блоков, видимость пинов и текущие значения переменных
не считаются изменением программы. Наблюдатель не компилирует сам и не заменяет
`LPLC.run`. Без результата сборки или сохранённой загрузки сравнение неизвестно.
Совпадение означает сравнение с последней подтверждённой загрузкой,
а не чтение текущей прошивки с устройства.

Trace реализован в [LplcViewProvider](../../WebUI/Views/Lplc/LplcViewProvider.cs)
через отдельную переменную-наблюдатель выхода. До появления данных её состояние
не подменяется нулём. `LP_Program.Retag` связывает наблюдатель с меркером;
[LplcGraphController](../../WebUI/Views/Lplc/LplcGraphController.cs) проецирует
значение на выход без дополнительного элемента диаграммы.

`LP_Program` сообщает ошибки с путём блока и строкой его исходника.
`/$YS/MQTT-SN/DPLC_verbose` добавляет дамп сгенерированного JS; Debug-запись
не накапливается в истории журнала и требует показа Debug в IDE.
Диагностика исходника не зависит от этого флага.
Карта Generator и диапазоны CodeLines позволяют связывать PC остановленной VM
с блоком. После потери кэша карта восстанавливается локальной компиляцией
и сверкой с `LPLC.loaded`; при несовпадении нельзя приписывать PC новому исходнику.

## Проверки и сопровождение

Изменение блока может затрагивать каталог, Binder/Generator, схему выходов,
общую конфигурацию и WebUI. Изменение ABI относится также к DPLC и прошивке.
Схема `args/in/out`, импорты типов и миграция сохранённых экземпляров —
разные операции; обновление каталога не исправляет экземпляры автоматически.
