# DPLC

DPLC — компилятор подмножества JavaScript в байткод стековой VM устройства.
Код находится в пространстве имён `X13.DevicePLC` и собирается внутри
[MQTT_SN.csproj](../MQTT_SN.csproj), а не отдельным проектом.

Входом служит либо текст DevicePLC (`pa0/src`), либо программа, сгенерированная
[LogramPLC](../LPLC/LPLC.md) для `pa1`. NiL.JS используется для получения
абстрактного синтаксического дерева — AST (Abstract Syntax Tree);
исходник PLC не исполняется на сервере как обычный JavaScript.
Передача результата устройству, подтверждения и команды запуска/остановки
находятся вне этой папки — в [DevicePLC.cs](../DevicePLC.cs).

## Ответственность и контракт

**Задача.** Получить из поддерживаемого исходника программу для выбранного
профиля устройства и сведения для привязки переменных/диагностики.
**Контракт.** Вход — текст, EP_Target и необязательное описание возможностей;
выход при успехе — байткод, граница RAM, меркеры и карта исходника.
Неуспех Parse запрещает использовать результат текущей сборки.

**Границы.** Поддержка синтаксиса в NiL.JS не означает поддержку в DPLC.
Компилятор не отправляет MQTT-SN, не изменяет физические GPIO и не подтверждает
совместимость установленной прошивки. Типы данных обмена шире языка PLC.
Форматы описаний Topic находятся в [справочнике](../../../Server/Repository/TopicFields.md#устройства-и-программы-mqtt-sn),
а не в результатах Hex/StackBottom.

**Реализация.** [EP_Compiler](Compiler.cs), [EP_VP1](EP_VP1.cs),
[EP_VP2](EP_VP2.cs), [EP_Device](EP_Device.cs).
**Проверки.** [Связи правил с тестами](#диагностика-и-сопровождение);
тестовая VM не является прошивкой. Потребитель результата —
[сценарий Build/Run](../LPLC/LPLC.md#путь-build-и-run).

## Конвейер компиляции

**Задача и контракт.** Разделить анализ программы, вывод типов и генерацию так,
чтобы второй проход использовал уже согласованную модель символов.

Точка входа — `EP_Compiler.Parse(code)` в [Compiler.cs](Compiler.cs).
Для новой сборки вызывающий код создаёт компилятор с целевой платформой
и, при наличии, описанием устройства.

```text
исходник JavaScript
  → NiL.JS Module / AST
  → EP_VP1: объявления, области, поля, отложенные вызовы
  → размещение полей классов и InferTypes
  → EP_VP2: инструкции с типизированными операндами
  → размещение меркеров, оптимизация и связывание инструкций
  → Hex + StackBottom + varList/ioList + CodeLines
```

Размещение полей выполняется после полного первого прохода: поле может встретиться
не только в конструкторе, но и в методе либо внешнем обращении. Второй проход
уже использует смещения полей и размер экземпляра.

`EP_VP2` не является универсальным интерпретатором AST: неподдерживаемые конструкции
отклоняются. Возможности NiL.JS сами по себе не означают поддержку конструкции
целевой VM.

После генерации области оптимизируются и размещаются в ROM с выравниванием
начала области на 32 байта. `Hex` содержит адреса и массивы байтов областей,
а не Intel HEX-текст. Размер программы ограничен адресным пространством 64 KiB.
Это выравнивание и ограничения формата необходимо учитывать при изменении
инструкций или схемы загрузки.

**Границы.** Результат принадлежит этой сборке и выбранному профилю.
Оптимизация/размещение не являются проверкой реального объёма памяти всех
устройств. Проверки отдельных инструкций и типов не доказывают поддержку
любого JavaScript или исчерпывающее покрытие границы 64 KiB.
**Проверки.** Тесты языка перечислены [ниже](#диагностика-и-сопровождение);
ошибки и потребители результата раскрыты в контракте Parse.

### Контракт EP_Compiler.Parse и его потребители

Это программный интерфейс класса `EP_Compiler` из [Compiler.cs](Compiler.cs),
а не формат пакета MQTT-SN, каталога или ответа RPC.
Вызывающий компонент создаёт экземпляр `new EP_Compiler(target, device)`,
при необходимости подписывается на `CMsg`, затем вызывает `Parse(source)`.
Сам метод возвращает только `bool`; байткод и сопутствующие данные находятся
в полях/свойствах **того же экземпляра компилятора**.

| Результат | Смысл и потребитель |
|---|---|
| `Parse(source)` → `bool` | Только `true` разрешает использовать результаты текущей сборки; при `false` вызывающий код обрабатывает `compiler.Error`. |
| `compiler.Hex` | `SortedList<uint, byte[]>`: адрес → байты программы. Передаётся загрузчику. |
| `compiler.StackBottom` | Граница статически занятой RAM в байтах. Загрузчик переводит её в 32-битные слова через `(StackBottom + 3) / 4`. |
| `compiler.varList` | Имя переменной/поля → MQTT-SN-тег меркера. Используется для экспорта переменных и привязки наблюдателей LPLC. |
| `compiler.ioList` | Объектные I/O-теги программы DevicePLC (`pa0`), которые нужно зарегистрировать перед запуском; это не входы/выходы блоков LogramPLC. |
| `compiler.CodeLines` | Интервалы адресов команд и строки исходника; основа `SourceLineAt(pc)` и обратного отображения ошибок LPLC. |
| `compiler.CMsg` | Событие диагностики во время компиляции; путь топика добавляет подписчик. |
| `compiler.Error` | Причина неуспешного Parse; не заменяет возвращаемый флаг успеха. |

Два конкретных пути использования:

- **DevicePLC (`pa0`):** `DevicePLC.Compile` читает `src`, вызывает Parse
  и переносит Hex/StackBottom/varList/ioList в свой внутренний `PlcProgram`.
  Build ограничивается сборкой; Run использует этот результат для регистрации
  объектов и загрузки. См. [DevicePLC.cs](../DevicePLC.cs).
- **LogramPLC (`pa1`):** `LP_DiagramCompiler.Run` передаёт компилятору JS,
  созданный Generator, и переводит varList/CodeLines/диагностику обратно
  в элементы диаграммы. Через `LP_Program` результат попадает в тот же загрузчик
  DevicePLC. См. [LP_DiagramCompiler.cs](../LPLC/LP_DiagramCompiler.cs)
  и [LP_Program.cs](../LPLC/LP_Program.cs).

## Профили PLC и типы данных

Профиль выбирается в `DevicePLC.TargetOf` и передаётся через `EP_Target`
из [EP_Enums.cs](EP_Enums.cs). Разделение следует описывать по интерфейсу:

- `pa0` — **DevicePLC**: текстовый исходник, объектные I/O-теги устройства.
- `pa1` — **LogramPLC**: диаграмма, GPIO и порты через блоки/вызовы API.
  Самостоятельных I/O-переменных, `Ta*`/`Sa*` и suppressed здесь нет;
  используются `AvailablePins`/`AvailableUarts`.

Названия аппаратных платформ не являются определением этих профилей.
Общий компилятор и протокол загрузки не гарантируют взаимозаменяемости программ:
набор native API и доступная модель периферии различаются.
В профиле `pa1` обращения к объектным I/O-тегам отклоняются;
для GPIO используется `Pin` и описание устройства.

### Поддерживаемые типы исходника

Скалярные типы переменных и полей, явно обрабатываемые
[EP_VP1](EP_VP1.cs) и [EP_VP2](EP_VP2.cs):

| Тип | Хранение/диапазон | Объявление | Префикс меркера |
|---|---|---|---|
| `Boolean` | Логическое значение, 1 бит в статическом хранилище | `new Boolean(false)` | `Mz` |
| `Int8` | Знаковое 8-битное, -128..127 | `new Int8(0)` | `Mb` |
| `UInt8` | Беззнаковое 8-битное, 0..255 | `new UInt8(0)` | `MB` |
| `Int16` | Знаковое 16-битное, -32768..32767 | `new Int16(0)` | `Mw` |
| `UInt16` | Беззнаковое 16-битное, 0..65535 | `new UInt16(0)` | `MW` |
| `Int32` | Знаковое 32-битное, -2147483648..2147483647 | `new Int32(0)` | `Md` |
| `Float` | 32-битное IEEE-754 | `new Float(0)` | `Mf` |

Диапазоны описывают представление хранения, не универсальную проверку
входных значений на переполнение. Локальные значения и параметры используют
ячейки стека VM, а не отдельную 8/16-битную ячейку на каждую переменную.
Без явного типа компилятор выводит его из инициализаторов, присваиваний,
аргументов и возвращаемых значений.

Дополнительно поддерживаются:

- Константные массивы ROM: `Uint8Array`, `Int8Array`, `Uint16Array`,
  `Int16Array`, `Int32Array`, объявленные с массивом значений.
  Например, `var table = new Uint8Array([0, 128, 255]);`.
  Чтение по индексу использует `CHECK_IDX` и `ElementCount`;
  это не изменяемые динамические JS-массивы.
- Экземпляры объявленных классов с конструктором, полями и методами;
  отдельный встроенный класс `Pin`. Поля и размеры экземпляров
  размечаются компилятором, а не произвольным JS-объектом во время исполнения.
- Преобразования `Int32(x)`, `UInt32(x)`, `Float(x)`.
  `UInt32` — беззнаковая интерпретация 32-битного значения на стеке,
  а не отдельный тип меркера или поддержка `new UInt32(...)`.
- Сдвиги `<<`, `>>`, `>>>` на константу — одна команда `LSL`/`ASR`/`LSR`;
  на значение выражения — цикл из сдвигов на 1 бит, число бит `& 31`, как в JS.
  Отдельной команды сдвига со стека в VM нет.
- Константная байтовая строка как специальный аргумент PrintF;
  это не общий строковый тип VM.

Регистр имён важен: скалярный `UInt8`, но массив `Uint8Array`.
Общие `String`, `Object`/динамические массивы, `Int64`/`UInt64`,
`Double`/`Float64Array`, `Uint32Array` и `Float32Array` не входят
в перечисленные типы DPLC. Типы, передаваемые MQTT-SN, например строки,
массивы байт и 64-битные значения, не следует автоматически считать
типами исходника PLC.

### Внутренние категории типов

Нужно различать три уровня типов:

1. `EP_Type` — категория символа/хранилища: меркер, поле, локальная переменная,
   параметр, массив, функция, класс, API и другие.
2. `EP_ValType` — представление значения на стеке: `Int`, `UInt`, `Float`.
   `UInt` важен, в частности, при преобразовании в float.
3. Теги меркеров — представление значений для MQTT-SN/Repository:
   например `Mz`, `Mb`, `MB`, `Mw`, `MW`, `Md`, `Mf`.

Float — 32-битный IEEE-754 в той же ячейке стека, что и целое значение.
Выбор float-инструкций и преобразований должен согласовываться с прошивкой.
У обычных JS-функций типы параметров и результатов выводятся из программы;
для категорий без собственного float-варианта используется `isFloat`.

### Модель символа Merker

В [Compiler.cs](Compiler.cs) `Merker` объединяет сведения о символе, его области
и размещении. Сигнатуру API и размеры данных нельзя подменять друг другом:

- `ParameterTypes` — типы аргументов native API в порядке исходника.
- `ResultType` — тип результата native API; `null` означает отсутствие результата.
- `ElementCount` — число элементов константного массива для проверки индекса.
- `InstanceWords` — размер экземпляра/Pin в 32-битных словах.

Количество аргументов API берётся из `ParameterTypes`, приведение каждого
аргумента — из соответствующего элемента массива, а `ResultType` участвует
в выводе типов выражений. Размер массива и размер экземпляра не являются
сигнатурой функции. Сигнатуры обычных JS-функций по-прежнему выводятся через
параметры и `isFloat`; их нельзя заменять контрактом native API.

## Описание устройства и GPIO

[EP_Device](EP_Device.cs) получает поле `PLC` из состояния типа устройства
в `/$YS/TYPES`. Вызывающий слой загружает описание при компиляции;
сам компилятор не ищет модель устройства в Repository.
Это `State.PLC` топика `/$YS/TYPES/MQTT-SN/<имя типа>`.
`Manifest.type` экземпляра устройства указывает на этот тип,
а отчёты `AvailablePins`/`AvailableUarts` находятся в Manifest экземпляра.
Описание программного блока — другой топик.
Источники типов опубликованы в
[каталоге устройств](https://enviriot.github.io/catalog/mqtt-sn/);
состав State, Manifest и детей разобран в
[обзоре топика типа устройства](../MQTT_SN.md#топик-типа-устройства).

**Задача и контракт.** EP_Device проверяет описание режимов и пинов,
а компиляция использует его для разрешения имён и допустимости операций.
Формат names/groups/pins/modes/opt и поведение при отсутствии описания —
в [TopicFields](../../../Server/Repository/TopicFields.md#устройства-и-программы-mqtt-sn).

Один режим может встречаться в нескольких группах, но его `v`, `io` и `opt`
должны согласовываться. Пин допустим, если входит хотя бы в одну группу режима.

Общая модель возможностей и разрешение аргументов живут в
[ConstructorResolver.cs](../../../Server/Plc/ConstructorResolver.cs),
а схема аргументов — в
[ConstructorSchema.cs](../../../Server/Plc/ConstructorSchema.cs).
Редактор и компилятор должны использовать одни ограничения, а не независимые
таблицы GPIO.

**Границы.** Корректное описание не доказывает фактическую доступность
аппаратуры; отчёты экземпляра ограничивают его отдельно.
**Проверки.** [DevicePlcDeviceTests.Groups_GiveConstantsAndPins](../../../Tests/MQTT_SN/DevicePlcDeviceTests.cs)
проверяет разбор констант и пинов; ограничения выбора ресурсов —
[ConstructorConfigurationTests.AvailabilityRetainsHighPinsAndIndependentMissingMasks](../../../Tests/ConstructorConfigurationTests.cs).

В профиле LogramPLC поддерживается `ConfigPin(pin, mode, option)`, API 31.
Прежние пронумерованные имена функций настройки не поддерживаются;
старый рукописный исходник требует явной правки.
Правила `defaultPin`, выбора шины и аргументов TwiMaster описаны в
[LPLC](../LPLC/LPLC.md#twi-master).

### Отчёты доступности ресурсов

В профиле LogramPLC (`pa1`) дополнительно к типу устройства применяются
AvailablePins/AvailableUarts. Формат и владельцы этих полей описаны
в [TopicFields](../../../Server/Repository/TopicFields.md#mqtt-sn).

Это ресурсы, доступные PLC, а не список ресурсов, ещё не занятых блоками.
Каждая отсутствующая маска независимо оставляет только ограничения типа;
нулевая маска означает отсутствие доступных ресурсов.
Маски не свидетельствуют о поддержке конкретной версии PrintF.

Граница ответственности:

- [MsDevice](../MsDevice.cs) принимает отчёты, проверяет длину и сохраняет
  последнее корректное значение. Отчёты принадлежат устройству, не отправляются
  ему обратно и не выделяются как меркеры.
- Clean reconnect сбрасывает отслеживание дубликатов, но не последние отчёты.
- [ManifestTreeController](../../WebUI/Views/InspectorManifest/ManifestTreeController.cs)
  и [ManifestRpcDispatcher](../../WebUI/Views/InspectorManifest/ManifestRpcDispatcher.cs)
  запрещают их изменение/удаление, в том числе через замену родительского объекта.
- `EP_Device` и общие классы `Server.Plc` используют отчёты для проверки программы.

## API состояния, времени и периферии

Раздел дополняет описание native API сведениями из исходной заметки `api.txt`.
Номера, сигнатуры и доступность сверены с `LoadNativeFunctions` в
[Compiler.cs](Compiler.cs) и
[DevicePlcApiTests](../../../Tests/MQTT_SN/DevicePlcApiTests.cs).
Компилятор задаёт ABI вызова, но сам не реализует часы, UART или TWI:
их поведение обеспечивает прошивка.

В таблицах `Int` означает 32-битное значение стека, `void` — отсутствие
результата. Обозначения `s4`/`u1` в исходной заметке относятся соответственно
к 32-битному слову и байту данных; аргументы перечисленных API передаются
на стеке как `Int`.

### Состояние узла и время

Эти вызовы доступны компилятору в обоих профилях, `pa0` и `pa1`.

| Вызов | API | Результат |
|---|---:|---|
| `NodeStatus()` | 5 | Int: 0 — нет соединения, 1 — соединение установлено. |
| `getMilliseconds()` | 6 | Int: значение времени в миллисекундах. |
| `getSeconds()` | 7 | Int: значение времени в секундах. |
| `Random()` | 8 | Int: случайное значение. |
| `NowSeconds()` | 9 | Int: число секунд с 00:00:00 текущего дня. |
| `Today()` | 10 | Int: упакованные год, месяц, день и день недели. |

Формат результата Today, от старшего байта к младшему:

| Биты | Поле | Значения |
|---|---|---|
| 31..24 | Год | 0..99; век в слове не хранится. |
| 23..16 | Месяц | 1..12. |
| 15..8 | День месяца | 1..31. |
| 7..0 | День недели | 1 — понедельник, …, 7 — воскресенье. |

```text
Today = (year << 24) | (month << 16) | (day << 8) | dayOfWeek
```

### TWI: управление и данные

Вызовы без номера шины доступны в обоих профилях. Для LogramPLC дополнительно
есть варианты с первым аргументом `bus`; его номер начинается с нуля.
Это native API программы устройства, не серверный `TwiReq`.

| Вызов | API | Результат | Вариант с номером шины, только `pa1` |
|---|---:|---|---|
| `TwiControl(control)` | 1 | void | `TwiBusControl(bus, control)`, API 40 |
| `TwiStatus()` | 2 | Int: упакованное состояние | `TwiBusStatus(bus)`, API 41 |
| `TwiPutByte(data)` | 3 | void; очередной байт записи | `TwiBusPutByte(bus, data)`, API 42 |
| `TwiGetByte()` | 4 | Int: очередной байт чтения | `TwiBusGetByte(bus)`, API 43 |

Перед использованием TWI в LogramPLC шина должна быть сконфигурирована
через [TwiMaster](../LPLC/LPLC.md#twi-master).

#### Слово TwiControl

Аргумент control содержит четыре 8-битных поля:

| Биты | Поле |
|---|---|
| 31..24 | Количество байт для чтения. |
| 23..16 | Количество байт для записи. |
| 15..8 | Режим доступа: `TWI_WRITE = 0x01`, `TWI_READ = 0x02`; сочетание — `0x03`. |
| 7..0 | Адрес устройства. |

```text
control = (readCount << 24) | (writeCount << 16) | (access << 8) | address
```

`0x1A010376` означает чтение 26 байт, запись одного байта,
доступ Read/Write и адрес `0x76`, например для BME280.
Это расположение полей внутри числа, не описание порядка байт транспорта.

#### Слово TwiStatus

| Биты | Поле |
|---|---|
| 31..24 | Количество прочитанных байт, доступных для получения. |
| 23..16 | Количество записанных байт. |
| 15..8 | Флаги состояния. |
| 7..0 | Адрес устройства. |

Флаги относятся к байту состояния; маска всего слова сдвинута на 8 бит:

| Обозначение | Байт состояния | Маска слова | Смысл |
|---|---|---|---|
| `TWI_WD_ARMED` | `0x04` | `0x0400` | Watchdog запущен. |
| `TWI_BUSY` | `0x08` | `0x0800` | Шина занята. |
| `TWI_RDY` | `0x10` | `0x1000` | Обмен завершён. |
| `TWI_WD` | `0x20` | `0x2000` | Тайм-аут. |
| `TWI_SLANACK` | `0x40` | `0x4000` | NACK адреса: устройство не ответило. |
| `TWI_ERROR` | `0x80` | `0x8000` | Неизвестная/внутренняя ошибка. |

Названия TWI-флагов здесь обозначают биты, а не автоматически доступные
глобальные константы JavaScript.
Маска ошибок всего слова — `0xE000`, не `0xE0`.

Пример завершённого обмена: `0x08011076` — адрес `0x76`,
один записанный байт, восемь байт для чтения, установлен `TWI_RDY`.

#### Последовательность обмена

Для описанного в заметке API TwiControl/TwiStatus/TwiPutByte/TwiGetByte:

1. Убедиться, что шина свободна, и задать управляющее слово.
2. Передать через TwiPutByte все объявленные байты записи.
   Обмен с записью начинается только после заполнения этих данных.
3. Опросить TwiStatus до завершения или ошибки.
4. Получить все принятые байты через TwiGetByte; только после их чтения
   шина освобождается. Вызов TwiStatus сбрасывает указатель чтения,
   поэтому его нельзя вставлять между последовательными TwiGetByte
   при получении одного ответа.

Проба адреса без записи/чтения в API с номером шины — отдельный случай:
чтение конечного TwiBusStatus закрывает такую транзакцию.
Он используется в [SCAN_BUS](../LPLC/LPLC.md#scan_bus).

### UART: инициализация и обмен

| Вызов | API | Доступность и результат |
|---|---:|---|
| `UartInit(nr, mode)` | 20 | Только DevicePLC (`pa0`), void. Инициализация порта с кодом режима. |
| `UartBytesToRead(nr)` | 21 | Оба профиля, Int: количество доступных байт приёма. |
| `UartGetByte(nr)` | 22 | Оба профиля, Int: чтение байта. |
| `UartPutByte(nr, data)` | 23 | Оба профиля, Int: код результата записи байта; `>0 = запись принята`, `<=0 = нет места/ошибка` |

Для UartInit младшие четыре бита mode (`mode & 0x0F`) задают **код скорости**,
а не число бод:

| Код | Скорость, бод |
|---:|---:|
| 0 | 2400 |
| 1 | 4800 |
| 2 | 9600 |
| 3 | 19200 |
| 4 | 38400 |
| 5 | 57600 |
| 6 | 115200 |

Бит `0x10` включает RS-485; например, mode `0x12` означает 9600 бод с RS-485.
В `pa1` UartInit недоступен: конфигурацию выполняют ConfigPin и блок
[SerialPort](../LPLC/LPLC.md#serialport).


## Потоковые API LogramPLC и PrintF

Компилятор формирует вызовы API, но буферы UART, выполнение транзакций и журнал
реализованы прошивкой. Описанные ниже ограничения исполнения — контракт
совместимой прошивки, не реализация очередей на сервере.

| Вызов/константа | Контракт |
|---|---|
| `SendByte(stream, value)` | API 23; передаётся младший байт, включая 00/FF. |
| `UartPutByte` | Совместимое имя API 23. |
| `PrintF(stream, "format", ...)` | API 26; формат компилируется в ROM. |
| `LOG_DEBUG`, `LOG_INFO`, `LOG_WARN`, `LOG_ERROR` | Потоки `0xFFE0`, `0xFFE1`, `0xFFE2`, `0xFFE3`. |

Для SendByte и PrintF действует тот же контракт: `>0 = запись принята`, `<=0 = нет места/ошибка`.
Неиспользуемый результат удаляется со стека. Принятие в буфер не является
подтверждением окончания физической передачи. Аргументы вычисляются при каждом
вызове; автоматического повтора, снимка аргументов и очереди сообщений блока нет.

### Формат и ABI

[EP_PrintF.Arguments](EP_PrintF.cs) проверяет константную строку формата.
Допустимы символы U+0000..U+00FF; длина должна помещаться в адресное пространство VM.
Пользовательскому исходнику не нужен отдельный Uint8Array.

| Преобразование | Тип аргумента |
|---|---|
| `%c`, `%d` | Int32 |
| `%x`, `%X` | UInt32; соответственно нижний/верхний регистр шестнадцатеричных цифр |
| `%f` | Float32 |
| `%%` | Аргумента нет |

Числовые преобразования допускают ширину 1..9 и флаг `0` либо `-`;
флаг требует ширины. Float допускает точность 0..8, по умолчанию 6.
Для `%c` ширина и точность не разрешены. Примеры:
`%02d`, `%08x`, `%08X`, `%.2f`, `%-5.1f`.
Нуль внутри формата — байт данных, а не конец C-строки.
Парсер допускает не более 256 аргументов-значений и проверяет их количество
на соответствие формату при компиляции вызова.

Вызов преобразуется к ABI:

```text
(stream, offset, length, count, values...)
```

`offset` и `length` описывают формат в ROM, `count` — число значений.
В описании native API находятся четыре Int заголовка и результат Int;
типы остальных значений определяются отдельно по каждому формату.
Генерацию вызова выполняет [EP_VP2](EP_VP2.cs).
Порядок стека остальных API этим специальным преобразованием не меняется.

### Ограничения исполнения

Для совместимой прошивки сохраняется следующий контракт:

- Результат PrintF длиной до 256 байт принимается целиком либо поток не меняется.
- Для журнала каждая часть между нулями ограничена 43 байтами; записи ASCII,
  завершение — нулём или границей цикла.
- Журнал работает по возможности, с очередью на 16 записей; код PLC не должен
  блокироваться в ожидании журнала.
- Слишком длинный результат, неверный формат/адрес/count — ошибка `0x8A`;
  нехватка стека — `0x87`.

Обновление требует согласованных сервера и прошивки, повторных Build/Run
и совместимых описаний блоков из
[каталога LPLC](https://enviriot.github.io/catalog/LPLC/).
Актуальные State.LPLC.src типов BME280/HDC1080 используют PrintF.
Состав топиков типов и экземпляров разобран в
[LPLC](../LPLC/LPLC.md#топики-типов-и-экземпляров-logramplc).
Исходников прошивки в этой папке нет.

## Диагностика и сопровождение

**Задача и контракт.** Отнести ошибку к исходнику пользователя, а не потерять
её в сгенерированном JS или вывести повторно без контекста.

`CMsg` позволяет вызывающему слою добавлять контекст. При отсутствии подписчика
компилятор сам сообщает о неуспехе; при наличии подписчика ответственность за
сообщение с путём исходника остаётся у вызывающего слоя.

- Для `pa0` [DevicePLC](../DevicePLC.cs) указывает путь `src` и координаты.
- Для `pa1` [LP_DiagramCompiler](../LPLC/LP_DiagramCompiler.cs) переводит строки
  сгенерированной программы и адреса команд в блок и строку его исходника.
- Отладочные дампы управляются `/$YS/MQTT-SN/DPLC_verbose`;
  ошибки/предупреждения исходника не требуют включения этого флага.

При добавлении инструкции или API нужно согласовать коды/типы,
генерацию в VP2, вывод типов/сигнатуру, описание устройства при необходимости
и контракт прошивки. Для изменений языка важны оба прохода, а не только
обработчик генерации инструкции.

**Реализация.** `EP_Compiler.CMsg`, `Where`, `SourceLineAt`,
[LP_DiagramCompiler](../LPLC/LP_DiagramCompiler.cs) и [DevicePLC](../DevicePLC.cs).
**Границы.** Адрес PC можно сопоставлять только с результатом той же программы.
Диагностика компилятора не покрывает все ошибки исполнения или транспорта.

| Без подписчика отказ всё равно диагностируется | [PlcDiagnosticsTests.StandaloneCompilerStillReportsFailures](../../../Tests/MQTT_SN/PlcDiagnosticsTests.cs). |
