# MQTT_SN

MQTT_SN — серверный плагин Enviriot, связывающий устройства MQTT-SN с Repository
через последовательные и UDP-шлюзы. Помимо протокола и синхронизации значений,
он содержит серверное расширение TWI, компилятор PLC и поддержку диаграмм LogramPLC.
Этот документ описывает содержимое папки и границы компонентов для разработчика.

Подробные обзоры подсистем:

- [DPLC — компилятор, типы, VM и native API](DPLC/DPLC.md).
- [LPLC — модель диаграммы, каталог и интеграция с Repository/WebUI](LPLC/LPLC.md).

## Сборка и зависимости

[MQTT_SN.csproj](MQTT_SN.csproj) собирает библиотеку `MQTT_SN` для .NET Framework 4.8.
Проект ссылается на [Server](../../Server/Server.csproj) и NiL.JS 2.6.1722;
MEF используется для экспорта `IPlugModul`.
При компиляции PLC NiL.JS используется для получения абстрактного синтаксического
дерева — AST (Abstract Syntax Tree). Серверные TWI-драйверы, напротив,
исполняются самим NiL.JS.

Основные пространства имён: `X13.Periphery` для плагина, шлюзов и устройств,
`X13.DevicePLC` для DPLC, `X13.LogramPLC` для LPLC.
Версионные атрибуты подключаются из генерируемого сервером VersionInfo;
[Properties/AssemblyInfo.cs](Properties/AssemblyInfo.cs) содержит остальные
метаданные и `InternalsVisibleTo("X13.Tests")`.

Debug/Release помещают сборки в общие каталоги
`Output\bin_d`/`Output\bin_r`. `obj` — промежуточный результат сборки,
не часть архитектуры плагина.
Порядок сборки и проверки репозитория описан в [CLAUDE.md](../../CLAUDE.md).

## Жизненный цикл

[MQTT_SNPl](MQTT_SNPl.cs) экспортируется как `IPlugModul`
с именем `MQTT_SN` и приоритетом 7.

1. `Init` регистрирует RPC и подписку на поле `MQTT-SN.model`,
   создаёт `LP_Schema.Watcher` и `LP_Status.Watcher`.
   Наблюдатели нужны и для offline-редактирования, до регистрации `pa1` устройством.
2. `Start` применяет настройки, импортирует встроенный каталог LPLC,
   затем создаёт UDP-шлюз и запускает поиск последовательных портов.
   Каталог должен существовать до первого подключившегося устройства.
3. `Tick` обслуживает устройства, шлюзы и обновление статусов LPLC.
4. `Stop` освобождает подписки плагина/наблюдателей и вызывает Stop шлюзов.

Топик-владелец — `/$YS/MQTT-SN`. Его Boolean State представляет `enabled`
для контракта плагина; при первоначальном создании устанавливается true
и атрибуты Required/Readonly/Config.

## Шлюзы, сообщения и устройства

### Входной поток

```text
Serial / UDP
  → шлюз и границы кадра
  → MQTT_SNPl.ProcessInPacket / MsMessage.TryParse
  → обнаружение шлюза, DHCP_REQ или CONNECT
  → MsDevice.ProcessInPacket для существующей сессии
  → значение Repository либо IMsExt.Recv
```

[MsMessage.TryReadHeader](MsMessages.cs) проверяет длину и формат заголовка;
`TryParse` разбирает тело и возвращает `MsParseError`.
Ошибки TooShort/BadLength/UnknownType/Malformed — ошибки входных данных,
не успешные пустые сообщения.

[MsGUdp](MsGUdp.cs) дополнительно проверяет заголовок до фильтрации
CONNECT/SEARCHGW. Его `RejectFrame` ограничивает частоту предупреждений
об отказах датаграмм. Это не универсальное ограничение всех предупреждений:
общая диагностика разбора в [MQTT_SNPl](MQTT_SNPl.cs) зависит от `verbose`,
а последовательный транспорт отдельно проверяет границы/длину кадра.

UDP использует порт 1883. Последовательный транспорт открывает порт
с 38400/8N1. Это настройки связи сервера со шлюзом, не параметры UART
блока [LPLC/SerialPort](LPLC/LPLC.md#serialport).

### Идентичность и состояние

При CONNECT устройство ищется по ClientId/имени независимо от текущего шлюза.
Новый узел создаётся в `/dev/<ClientId>` с редактором `MsStatus`
и полем `MQTT-SN.model`. При смене шлюза существующее устройство используется
повторно; имена устройств должны быть уникальны в сети.

Нужно различать:

- имя устройства/ClientId;
- локальный путь топика Repository;
- `MQTT-SN.tag` — имя объекта/поля в обмене с устройством;
- числовой TopicId, согласованный регистрацией.

Переименование локального сигнала само по себе не переименовывает его тег.
Изменение тега существующей регистрации инициирует unregister/register.
Для имени самого подключённого устройства существует отдельная передача
нового имени через предопределённый объект `0xFF00`.

Внутренние состояния сессии подробнее внешнего State:
Connected/AWake отображаются как `st: 1`, ASleep как `st: 2`,
остальные — `st: 0`. Для доступного/спящего узла добавляется `via`.
Отображение находится в
[display-editors.js](../../Output/www/ide/editors/display-editors.js).

Сам [MsDevice](MsDevice.cs) реализует `IMsGate`: доступный узел может
пересылать инкапсулированные сообщения соседних устройств.

### Устройства без PLC, DevicePLC и LogramPLC

Наличие MQTT-SN не означает наличие ресурсов для исполнения PLC.
Разделение определяется возможностями прошивки и объектом управления,
а не производителем, названием платы или микроконтроллера.

| Категория | Объект управления | Данные и периферия |
|---|---|---|
| Без PLC | Нет `pa0`/`pa1` | Самостоятельные переменные входов/выходов; `Ta*`/`Sa*` только при поддержке соответствующих интерфейсов прошивкой. Например, устройства A1–A5 на AVR: ресурсов для PLC недостаточно. |
| DevicePLC | `pa0`, тип `Ext/DevicePLC` | Текстовый исходник `pa0/src`, переменные программы; сохраняется объектная модель входов/выходов и поддерживаемых прошивкой `Ta*`/`Sa*`. |
| LogramPLC | `pa1`, тип `Ext/LogramPLC` | Диаграмма, M-переменные и наблюдатели. GPIO, UART и TWI обслуживаются программой через блоки/API, а не самостоятельными I/O-объектами устройства. |

У `pa1` нет переменных аппаратных входов/выходов объектной модели,
объектов `Ta*` (ServerTWI) и `Sa*` (последовательный обмен).
Соответственно, `MQTT-SN.suppressed`/`SupressInputs` к этому профилю не относятся.
Вместо описания такого набора объектов используются возможности из `PLC`
типа устройства и отчёты `AvailablePins`/`AvailableUarts`.
Входы/выходы **блоков диаграммы** (`LPLC.in`/`LPLC.out`) и M-переменные
при этом существуют — их нельзя путать с отсутствующими I/O-объектами устройства.

Поле `Children` в State топика типа не обязано перечислять `pa0`/`pa1`: служебный объект
регистрирует само устройство, а [MsDevice](MsDevice.cs) назначает ему тип.
Поле `PLC` описывает конфигурацию GPIO для LogramPLC; это не универсальный
Boolean-признак наличия любого PLC. Например, описание DevicePLC может
не содержать этого поля.

## Типы и экземпляры в дереве топиков

Ниже описываются топики: их имена, пути, State, Manifest, дети и потомки.
Общая модель и её файловое представление разделены в
[Server.md](../../Server/Server.md#общая-модель-топики).
Поиск, установка и обновление описаний из каталога относятся к
[WebUI](../WebUI/WebUI.md#каталог-типов).

| Ветвь дерева | Содержимое и источник описаний |
|---|---|
| `/$YS/TYPES/MQTT-SN` | Типы устройств из [mqtt-sn](https://enviriot.github.io/catalog/mqtt-sn/); группировка источников по производителям не определяет профиль PLC. |
| `/$YS/TYPES/TWI` | Типы ServerTWI-драйверов из [TWI](https://enviriot.github.io/catalog/TWI/); экземпляры исполняются на сервере и работают через `Ta*`. |
| `/$YS/TYPES/LPLC` | Типы блоков из [LPLC](https://enviriot.github.io/catalog/LPLC/); экземпляры входят в программу `pa1`. |

### Топик типа устройства

Имя типа берётся из части `MQTT-SN.model` до первой точки:
для `A1S10.<суффикс>` используется `/$YS/TYPES/MQTT-SN/A1S10`.
Это топик типа, а не конкретное устройство `/dev/<ClientId>`.

| Свойство | Топик типа | Экземпляр устройства |
|---|---|---|
| Имя | `A1S10` | ClientId, например `node1`. |
| Путь | `/$YS/TYPES/MQTT-SN/A1S10` | `/dev/node1`. |
| State | Описание редактора, действий, шаблонов объектов и возможностей. | Состояние устройства: `st`, при наличии связи — `via`. |
| Manifest | Атрибуты самого описания и его версия. | `type`, `MQTT-SN.model` и настройки данного устройства. |
| Дети и потомки | Не являются каналами конкретного устройства; шаблоны их создания находятся в State.Children. | Реальные топики сигналов, поддерживаемых интерфейсов и программ. |

Поля State топика типа:

| Поле | Смысл |
|---|---|
| `editor` | Представление состояния устройства, обычно `MsStatus`. |
| `hint`, `icon` | Описание и необязательная пиктограмма. |
| `Action` | Объявленные RPC-действия: объекты с `name` и `text`. Например, `MQTT_SN.SendDisconnect`. |
| `Children` | Шаблоны самостоятельных объектов устройства для Add; характерны для устройств без PLC и DevicePLC. |
| `mi` | Схема полей манифеста устройства; вложение `mi.MQTT-SN.mi.<поле>` задаёт редактор, default, атрибуты и другие метаданные. |
| `PLC` | Для LogramPLC — имена GPIO, группы, режимы и опции; см. [описание PLC](DPLC/DPLC.md#описание-устройства-и-gpio). |

Фрагмент `State.Children` топика `/$YS/TYPES/MQTT-SN/A1S10`
из [опубликованного описания](https://enviriot.github.io/catalog/mqtt-sn/Arduino/A1S10.xst):

```json
{
  "Ai00": {
    "default": 0,
    "manifest": {"MQTT-SN": {"tag": "Ai0"}, "type": "Integer"},
    "menu": "Analog input internal reference",
    "rc": "X9,X10",
    "hint": "Analog input internal reference, A0"
  }
}
```

Ключ `Ai00` — имя шаблона/создаваемого топика, `Ai0` — его сетевой тег.
`default` задаёт начальный State, `manifest` — манифест **экземпляра**,
`menu` — группу Add, `hint` — описание, `rc` — разделённые запятыми
обозначения ресурсов: `Xn` требует исключительного владения,
`Sn` допускает совместное владение с другими `Sn`.
Индекс n относится к нумерации ресурсов описания, не обязательно к номеру GPIO.
Ограничения `rc` обрабатывает [MenuBuilder](../WebUI/Helpers/MenuBuilder.cs);
это не маска `AvailablePins` и не описание аргументов LPLC.

В State типа устройства LogramPLC вместо набора I/O-шаблонов присутствует `PLC.groups`:
`pins` перечисляет допустимые GPIO, `modes` — режимы с `v`, `io`, `opt`,
при необходимости `defaultPin`. Формат можно сверить с
[описанием E1S10](https://enviriot.github.io/catalog/mqtt-sn/Espressif%20Systems/E1S10.xst),
но принадлежность к `pa1` не следует закреплять за именем этой модели.
`AvailablePins`/`AvailableUarts` приходят от экземпляра устройства во время обмена,
а не задаются статической маской в State топика типа.

## Топики и обмен значениями

`MsDevice.GetTopicInfo` сопоставляет топик, тег, TopicId и тип сериализации.
Предопределённые поля описаны в `PredefinedTopics`; типы обычных объектов —
префиксами `NTTable`. `MQTT-SN.tag = "---"` исключает служебный топик
из регистрации. Префиксы M-переменных без адреса резервируются для LPLC
и не регистрируются до назначения меркера.

Полученное значение проходит десериализацию и `MQTT-SN.convIn`,
затем записывается через `SetState`. Для предопределённых тегов с точкой
используется `SetField`; модель `<family>.<model>` связывает устройство
с типом `MQTT-SN/<family>`.

Обратный путь проходит через подписки Repository:

```text
изменение State / поддерживаемого поля MQTT-SN
  → PublishTopic / OwnerChanged
  → convOut и сериализация
  → очередь MsDevice
  → шлюз
```

Автор изменения позволяет не отправлять обычное принятое значение обратно
тому же устройству. Retained влияет на сохранение значения топика.
`convIn`/`convOut` исполняются в контексте с доступом к GetState/GetField.
Для устройств с самостоятельными I/O-объектами флаг `MQTT-SN.suppressed`
у входов преобразуется в общую маску `MQTT-SN.SupressInputs`;
написание этого имени является частью текущего контракта.
К LogramPLC (`pa1`) этот механизм не относится.

Отчёты `AvailablePins`/`AvailableUarts` обрабатываются отдельно:
это read-only данные устройства, не команды и не меркеры.
Формат, сохранение последнего корректного отчёта и ограничения компилятора
описаны в [DPLC](DPLC/DPLC.md#отчёты-доступности-ресурсов).

## Расширения TWI и PLC

[IMsExt](IMsExt.cs) отделяет транспорт сообщения от его прикладного содержимого.
`MsDevice` создаёт расширение при регистрации соответствующего тега.

### ServerTWI: исполнение и топики драйвера

Для `Ta*` устройств с объектным TWI-интерфейсом используется [TWI](TWI.cs).
У LogramPLC (`pa1`) таких объектов нет. Дочерние топики с типом `TWI*`
создают экземпляры JS-классов из поля `src` описания типа.
Драйвер получает GetState/SetState/GetField, TwiReq и таймеры.
TWI ведёт очередь запросов и сопоставляет ответы, длину, NACK и тайм-ауты;
значения драйвера становятся обычными топиками Repository.

Этот код исполняется на сервере. Он не является
[TwiMaster или SCAN_BUS](LPLC/LPLC.md#twi-master) из программы LogramPLC:
у них другой контекст исполнения и другой способ доступа к шине.

Типы ServerTWI — дети `/$YS/TYPES/TWI`, например топик с именем HDC1080
и путём `/$YS/TYPES/TWI/HDC1080`.
Источник: [опубликованное описание HDC1080](https://enviriot.github.io/catalog/TWI/HDC1080.xst).
Экземпляр драйвера размещается под топиком интерфейса, например
`/dev/node1/Ta0/HDC1080`; его дети T/H содержат результаты измерений.
Ниже перечислены поля **State топика типа**, а не поля Manifest экземпляра:

| Поле | Контракт |
|---|---|
| `src` | JS-класс, исполняемый NiL.JS на сервере. Конструктор обычно запускает опрос таймером; метод Tick не является обязательным интерфейсом драйвера. |
| `manifest.type` | Тип создаваемого экземпляра, например `TWI/HDC1080`. |
| `manifest.MQTT-SN.tag` | `---`: экземпляр драйвера не регистрируется как отдельный объект на устройстве. |
| `manifest.TWI` | Необязательные настройки экземпляра, интерпретируемые драйвером; например, `addr`. Их схему задаёт `mi.TWI.mi`. |
| `default` | Начальный State экземпляра, в этом примере 0. |
| `editor`, `enum` | Отображение State: в примере `Enum` и `TwiStatus`. Значение состояния изменяет сам драйвер. |
| `Children` | Шаблоны дочерних топиков; может быть пустым объектом, поскольку измерения создаются через SetState. |
| `hint`, `icon`, `mi` | Необязательные описание, пиктограмма и схема настроек. |

`Manifest.type = Ext/TwiDev` у топика типа относится к **описанию драйвера**.
`State.manifest.type = TWI/HDC1080` задаёт **шаблон Manifest экземпляра**.
После создания экземпляр имеет собственные State (статус), Manifest (тип,
настройки) и детей/потомков (измерения).
Эти уровни нельзя переставлять.

`TWI.addr` не имеет единой для всех драйверов семантики:
[BME280](https://enviriot.github.io/catalog/TWI/BME280.xst) вычисляет
`0x76 | (addr & 1)`, а
[INA226](https://enviriot.github.io/catalog/TWI/INA226.xst) использует
`addr & 0x7F` как полный адрес.
Сохранённое начальное значение берётся из `manifest.TWI.addr`;
`mi.TWI.mi.addr.default` — отдельные метаданные редактора.
Их нельзя без проверки заменять аргументом Address из формата LogramPLC.

`TwiDevice` добавляет в прототип класса GetState/SetState/GetField и TwiReq;
в контекст — setTimeout, setInterval, setAlarm.
`SetState("T", value)` создаёт при необходимости дочернее измерение
с `MQTT-SN.tag = "---"`. При удалении драйвера его таймеры освобождаются.

Формат аргумента `TwiReq`:

```text
[address, flags, writeLength, readLength, ...writeData]
```

Это массив байтового запроса к удалённому TWI, не вызов TwiBusControl из PLC.
Сервер требует минимум четыре элемента и сам записывает
`writeLength = arr.length - 4`; значения преобразуются в байты.
`flags` задаёт операцию интерфейса прошивки.
При успехе Promise-подобный результат получает весь ответ: заголовок из четырёх
байтов и данные начиная с `buf[4]`. В HDC1080 используются, например:

```js
this.TwiReq([0x40, 0x01, 0x01, 0x00, 0x00]);
this.TwiReq([0x40, 0x02, 0x00, 0x04]).then(this.RespT.bind(this), this.RespE.bind(this));
```

Сначала записывается указатель регистра, затем запрашиваются четыре байта.
Коды отклонения результата: 2 — timeout, 3 — NACK адреса,
4 — внутренняя ошибка, 5 — несовпадение длины ответа.
Для запроса без чтения (`readLength = 0`) TWI завершает запрос локально
синтетическим ответом: это не подтверждение физической операции периферией.

### Управление программой

`DevicePLC.TargetOf` выбирает профиль компиляции по объекту управления:

- DevicePLC (`pa0`) получает тип `Ext/DevicePLC` и дочерний `src` для текстовой программы;
- LogramPLC (`pa1`) получает `Ext/LogramPLC`, его программа читается из диаграммы,
  отдельного редактируемого `src` у программы нет.

Build компилирует без загрузки. Для типизированного `pa1` RPC умеет создать
`LP_Program` без подключённого узла. Run компилирует, обновляет привязки,
сравнивает CRC блоков, при необходимости останавливает PLC, передаёт изменённые
данные и запускает программу. Start/Stop отдельно управляют исполнением.

`DevicePLC` хранит автомат загрузки и обрабатывает подтверждения.
Части данных передаются блоками до 32 байт; граница статической RAM
переводится из байтов результата компилятора в слова протокола.
Состояние PLC (`0` unknown, `1` run, `2` stop) не является состоянием
соединения устройства.
Для LPLC подтверждённая загрузка дополнительно фиксируется в `LPLC.loaded`;
сравнение с диаграммой и восстановление места ошибки описаны в
[LPLC](LPLC/LPLC.md#интеграция-статусы-и-диагностика).

## RPC и интеграция с WebUI

| RPC | Обработчик/назначение |
|---|---|
| `MQTT_SN.RefreshPorts` | Запрос повторного сканирования последовательных портов. |
| `MQTT_SN.RefreshNIC` | Повторное обнаружение сетевых интерфейсов UDP-шлюза. |
| `MQTT_SN.SendDisconnect` | Отправка DISCONNECT и завершение сессии найденного устройства. |
| `MQTT_SN.PLC.Build` | Компиляция программы; для LPLC поддерживается offline-вызов. |
| `MQTT_SN.PLC.Run` | Компиляция и синхронизация программы с устройством. |
| `MQTT_SN.PLC.Start` | Запуск уже загруженной PLC. |
| `MQTT_SN.PLC.Stop` | Остановка PLC. |

Регистрация RPC не равна наличию команды UI. Общий
[TopicRpcDispatcher](../WebUI/Helpers/TopicRpcDispatcher.cs) допускает
действие через объявление `Action` топика/типа.
Действия PLC заданы в [base.xst](../../Server/Repository/base.xst)
и [LPLC.xst](LPLC/LPLC.xst); Refresh добавляется конфигурационным топикам
шлюзов. SendDisconnect объявлен в типах внешнего
[каталога устройств](https://enviriot.github.io/catalog/mqtt-sn/),
например в State типа [A1S10](https://enviriot.github.io/catalog/mqtt-sn/Arduino/A1S10.xst).

WebUI не компилирует PLC в браузере:
[LplcViewProvider](../WebUI/Views/Lplc/LplcViewProvider.cs),
[LplcPaletteBuilder](../WebUI/Views/Lplc/LplcPaletteBuilder.cs)
и [LplcGraphController](../WebUI/Views/Lplc/LplcGraphController.cs)
работают с деревом, схемами и результатами плагина.
Общие ограничения конструкторов/GPIO находятся в
[Server.Plc](../../Server/Plc).

## Конфигурация и диагностика

Настройки находятся под `/$YS/MQTT-SN`:

| Топик | Значение по умолчанию | Применение |
|---|---|---|
| `verbose` | true в Debug, false в Release | Подробный обмен шлюзов/устройств; подписка на изменения. |
| `DPLC_verbose` | true в Debug, false в Release | Компилятор/PLC и дамп generated JS LPLC; подписка на изменения. |
| `TWI_verbose` | true в Debug, false в Release | Серверное TWI-расширение; подписка на изменения. |
| `statistic` | false | Счётчики обмена в `stat` устройства; подписка на изменения. |
| `radius` | 1 | Значения 1–3 сохраняют смысл радиуса, остальные применяются как 0; шлюзы читают общее текущее значение. |
| `ports` | true при создании | Общий флаг поиска последовательных шлюзов. |
| `ports/<имя порта>` | true при создании | `false` запрещает сканирование этого порта; это не команда закрытия уже открытого шлюза. |
| `udp` | true при создании | Проверяется при создании UDP-шлюза; динамической подписки на переключение нет. |
| Дочерние строки `udp` | Сетевые адреса/маски | Читаются при инициализации; Refresh заново получает список из интерфейсов, а не просто перечитывает ручные значения. |

При запуске сохранённые `/$YS/DevicePLC/verbose` и `/$YS/TWI/verbose`
переносятся в новые пути. Уже настроенные новые значения имеют приоритет;
посторонние топики прежних папок сохраняются.

Ошибки и предупреждения исходника не зависят от verbose:
для `pa0` указываются путь `src` и координаты,
для LPLC — путь блока и строка его исходника.
Подробности владения диагностикой находятся в
[DPLC](DPLC/DPLC.md#диагностика-и-сопровождение) и
[LPLC](LPLC/LPLC.md#интеграция-статусы-и-диагностика).
Отображение журнала реализовано в
[log-panel.js](../../Output/www/ide/components/log-panel.js).
